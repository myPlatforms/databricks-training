# 알림(Alerts)

> 기준일: 2026-10-28 · 근거: 공식 문서

## 한눈에 보기

Databricks SQL **알림**(Alerts)은 쿼리 결과를 정해진 주기로 확인하고, 조건을 만족하면 알림 대상(notification destination)에 통지하는 기능입니다. 알림마다 자기만의 쿼리가 있고, 그 쿼리 결과에 조건을 겁니다. 평가할 때마다 상태가 정해집니다.

| 상태 | 의미 |
|---|---|
| `OK` | 조건을 만족하지 않음 |
| `TRIGGERED` | 조건을 만족함 |
| `ERROR` | 평가 중 오류 |

공식 문서는 기존 알림의 `UNKNOWN` 상태는 더 이상 쓰지 않는다고 명시합니다. 전환 기간에는 최신 알림과 기존(legacy) 알림이 함께 동작할 수 있습니다.

> **참고** 2026-08~10월 AI/BI 릴리즈 노트에는 알림 관련 항목이 없습니다. 이 페이지의 내용은 공식 알림 문서를 기준으로 합니다.

## 1. 왜 필요한가

### 이전 방식의 한계

- 매출이 기준 아래로 떨어졌는지 매일 대시보드를 열어 확인하는 일은 사람이 빠지면 멈춥니다.
- 대시보드는 사람이 보는 도구입니다. 임계값을 넘었을 때 **먼저 알려 주는** 역할은 하지 못합니다.
- 쿼리 결과를 스크립트로 확인하려면 스케줄러와 메신저 연동을 직접 만들어야 합니다.

알림은 쿼리, 조건, 스케줄, 알림 대상을 한 객체에 묶어, 조건이 맞을 때만 통지를 보냅니다.

## 2. 어떻게 동작하는가

### 구성 요소

공식 문서가 설명하는 알림의 구성 요소는 다음과 같습니다.

| 요소 | 설명 |
|---|---|
| 쿼리 | 알림마다 고유한 쿼리를 새 알림 편집기에서 씁니다. 쿼리는 알림의 일부입니다 |
| 조건 | 쿼리 결과에 대해 평가하는 조건 |
| 스케줄 | 쿼리를 정해진 주기로 실행하고, 실행마다 조건을 평가 |
| 알림 대상 | 상태가 바뀔 때 통지를 받을 대상. 문서는 **웹훅** 대상을 설명 |
| 평가 이력 | 과거 평가 결과를 알림 이력에서 확인 |

### 평가 흐름

1. 스케줄에 따라 알림의 쿼리가 실행됩니다.
2. 쿼리 결과에 조건을 적용해 `OK`, `TRIGGERED`, `ERROR` 중 하나로 평가합니다.
3. 상태가 바뀌면 알림 대상에 통지합니다. 웹훅 대상은 상태 변화 후 **JSON 페이로드** 를 받는다고 문서에 나옵니다.
4. 평가 결과는 이력에 남습니다.

### 쿼리 재사용의 제약

알림을 만들 때 **이미 저장된 SQL 쿼리를 재사용할 수 없습니다**. 공식 문서는 알림이 자기 쿼리를 가진다고 설명합니다. 같은 쿼리를 대시보드와 알림이 함께 쓰고 싶으면 쿼리를 두 번 작성하거나, 쿼리 내용을 동일하게 맞추는 방식으로 관리해야 합니다.

### 메트릭 뷰 측정값에 걸기

메트릭 뷰 소비 문서는 알림을 메트릭 뷰의 측정값을 모니터링하고 임계값을 넘으면 통지를 보내는 소비 경로로 설명합니다. 쿼리 안에서는 측정값을 `MEASURE()`로 감쌉니다. 자세한 쿼리 규칙은 [7페이지](metric-views-in-ai-bi.md)를 참고하십시오.

## 3. 어떻게 쓰는가

### 기본 절차

공식 문서 기준으로 알림을 만드는 흐름은 다음과 같습니다. 화면 위치와 메뉴 이름은 대상 워크스페이스 버전에 따라 다를 수 있으니 공식 문서의 절차 페이지에서 확인하십시오.

1. 알림 편집기를 열고, 알림 전용 쿼리를 작성합니다.
2. 쿼리 결과에 대한 조건을 정의합니다.
3. 평가 스케줄을 정합니다.
4. 알림 대상(예: 웹훅)을 연결합니다.
5. 이력에서 첫 평가가 `OK` 또는 `TRIGGERED`로 끝나는지 확인합니다.

쿼리는 조건에 필요한 최소한의 행과 열을 반환하도록 작성하십시오. 알림은 결과에 조건을 적용하는 것이므로, 쿼리가 무거우면 스케줄마다 그 비용이 듭니다.

### 알림 공유와 소유권

문서는 알림을 공유할 수 있고, 관리 페이지에서 소유권을 이전할 수 있다고 설명합니다. 공유 세부 권한(예: 어떤 권한이 있어야 알림을 편집하는지)은 이 문서 페이지에 나오지 않습니다. 운영 전에 권한 설정을 직접 확인하십시오.

## 4. 트레이드오프

- **알림은 간단하지만 쿼리를 따로 관리해야 합니다.** 대시보드의 데이터셋을 재사용할 수 없으므로, 같은 계산이 두 곳에 생길 수 있습니다.
- **웹훅은 어디든 연결할 수 있지만 페이로드 형식을 직접 처리해야 합니다.** 문서는 JSON 페이로드라고만 설명합니다. 세부 스키마는 문서에서 확인하지 않았습니다.
- **다른 알림 대상 종류는 이 문서에 설명이 없습니다.** 이메일이나 Slack 같은 대상이 가능한지는 이 장에서 확인하지 않았습니다. 대상 워크스페이스의 알림 대상 설정에서 확인하십시오.

### 언제 쓰지 않는가

- 실시간 스트리밍 이벤트에 반응해야 하는 경우. 알림은 스케줄마다 쿼리를 실행하는 방식입니다.
- 임계값 검사가 아니라 여러 시스템에 걸친 복잡한 워크플로우를 실행해야 하는 경우. 이때는 Lakeflow Jobs에서 조건 분기를 쓰는 편이 맞습니다. [4장 Lakeflow Jobs](../04-data-engineering/README.md)를 참고하십시오.

## 5. 주의사항

- **알림이 실행되는 자격 증명을 확인합니다.** 공식 알림 문서는 쿼리가 소유자의 권한으로 도는지, 다른 사용자의 권한으로 도는지 명시하지 않습니다. 권한이 바뀌었을 때 알림이 실패하지 않는지, 운영 전에 테스트하십시오.
- **`ERROR` 상태를 감시합니다.** 조건이 맞지 않아 `OK`인 것과 쿼리 실패로 `ERROR`인 것은 다릅니다. `ERROR`를 `OK`로 착각하면 장애를 놓칩니다.
- **`UNKNOWN` 상태에 기대지 않습니다.** 공식 문서는 이 상태를 지원하지 않는다고 명시합니다. 기존 알림을 옮길 때 이 상태를 보고 있던 로직을 고치십시오.
- **쿼리 재사용 제약을 설계에 넣습니다.** 저장된 쿼리를 알림에 바로 붙일 수 없습니다.
- **전환 기간의 혼재를 확인합니다.** 최신 알림과 기존 알림이 함께 있을 수 있으므로, 목록에서 어떤 것이 기존 알림인지 구분하십시오.
- **알림 대상의 소유자를 정합니다.** 웹훅 주소가 바뀌면 통지가 끊깁니다. 대상 관리 담당자를 정하십시오.
