# 베스트 프랙티스와 비용

> 기준일: 2026-10-28 · 근거: 공식 문서

이 페이지는 Lakebase를 운영할 때 설정으로 바로 확인할 수 있는 기준과, 문서에 적힌 과금 구조를 정리합니다. 단가(가격)는 이 페이지에서 다루지 않습니다. 공식 pricing 페이지에서 단가를 확인하지 못했기 때문입니다(아래 "비용 확인 방법" 참조).

## 1. 설계 기준

### 1.1 프로젝트와 브랜치를 나눈다

| 목적 | 권장 구조 | 근거 |
|---|---|---|
| 고객이나 애플리케이션을 완전히 분리 | 프로젝트를 분리 | 문서가 "isolated" 분리를 위해 여러 프로젝트를 만들 수 있다고 설명 |
| 개발·테스트·운영 분리 | 같은 프로젝트에서 브랜치 분리 | 브랜치는 역할과 데이터베이스를 격리 |
| 운영 데이터 보호 | 기본 브랜치 `production` 유지 | 기본 브랜치는 활성 컴퓨트 한도에서 예외 |

> **주의** 브랜치는 데이터를 격리하지만, 자식 브랜치는 부모의 변경을 자동으로 받지 않습니다. 운영 반영은 별도 마이그레이션 도구로 해야 합니다. 리셋은 부모에서 자식으로만 됩니다.

### 1.2 컴퓨트 크기는 범위로 잡는다

| 설정 | 문서 기준 값 |
|---|---|
| 1 CU | RAM 2 GB |
| Autoscaling 최대 | 64 CU (AWS 문서). 더 큰 고정 크기 컴퓨트는 문서상 최대 112 CU |
| 최소·최대 차이 | 16 CU 이하 (AWS 문서) |
| 스케일 투 제로 사용 가능 조건 | 최대 크기 32 CU 이하 (AWS 문서) |

- 최소 크기는 평소 부하의 하한으로 잡고, 최대는 피크 부하를 기준으로 잡습니다.
- 크기 변경은 활성 연결에 잠시 영향을 줄 수 있으므로, 업무 시간 외에 조정하는 것이 안전합니다.
- 문서는 데이터 크기보다 작업 집합(working set)이 중요하다는 취지로 설명하지만, 이 장에서는 작업 집합 측정 절차를 공식 문서 원문으로 확인하지 못했습니다. 측정 방법은 워크스페이스의 컴퓨트 메트릭 화면에서 확인하십시오.

> **참고** 과거 내부 자료에 있던 CU별 RAM 상세 표(shared_buffers, LFC 크기 등)는 이 장에서 쓰지 않습니다. 공식 문서 원문에서 확인하지 못했기 때문입니다.

### 1.3 스케일 투 제로를 쓸지 정한다

| 항목 | 값 (문서 기준) |
|---|---|
| 기본값 (새 프로젝트의 `production`) | 활성, 비활성 24시간 후 일시 중지 |
| 설정 가능 범위 | 최소 60초 ~ 최대 7일 |
| 끄는 방법 | 컴퓨트의 스케일 투 제로를 비활성화 (상상 가능한 항상 켜진 컴퓨트) |

- 간헐적으로 쓰는 개발 환경에는 스케일 투 제로가 맞습니다.
- 항상 응답해야 하는 운영 API에는 끄거나 긴 시간을 설정하는 것을 검토하십시오.
- 깨어나는 동안 첫 쿼리가 몇 초 지연될 수 있습니다(Apps 페이지 설명).

### 1.4 동시 활성 컴퓨트 한도를 기억한다

| 항목 | 값 |
|---|---|
| 프로젝트당 동시 활성 컴퓨트 | 기본 20 (기본 브랜치 제외) |
| 한도 초과 시 | 추가 컴퓨트는 일시 중지 상태로 남고, 접속 시 오류 |
| 한도 상향 | Databricks 지원팀 요청 |

여러 브랜치를 동시에 많이 켜 두면 이 한도에 걸릴 수 있습니다. 쓰지 않는 브랜치의 컴퓨트는 끄거나 스케일 투 제로를 설정하십시오.

### 1.5 읽기 복제본으로 읽기를 분산한다

- 브랜치당 읽기 복제본은 최대 6개입니다.
- 분석이나 보고서 쿼리를 읽기 복제본으로 보내면 주 컴퓨트 부하를 줄일 수 있습니다. 문서는 수평 읽기 확장과 읽기 전용 접근 용도로 설명합니다.
- 읽기 전용 풀러 연결은 고가용성(HA) 엔드포인트에서 읽기 접근을 켠 경우에만 사용할 수 있다고 문서가 설명합니다.

> **참고** 고가용성 구성의 보조 컴퓨트는 주 컴퓨트의 현재 CU보다 작게 줄일 수 없고, 스케일 투 제로도 쓸 수 없습니다(AWS 문서).

## 2. 연결 설계 기준

| 기준 | 설정 |
|---|---|
| 토큰 갱신 | 새 연결마다 발급하거나 만료 전에 갱신 |
| 재연결 | 유휴 24시간, 최대 연결 수명 3일을 전제로 지수 백오프 재시도 |
| 풀링 | 네이티브 비밀번호 역할 + 내장 PgBouncer 풀러 (OAuth와는 배타) |
| 세션 설정 | 트랜잭션 풀 모드에서는 `SET` 대신 `ALTER ROLE ... SET` |
| 장시간 작업 | 풀러 대신 직접 연결 |

자세한 내용은 [연결과 인증](connect-and-auth.md)을 참조하십시오.

## 3. 저장소, 기록 보존, 복구

### 3.1 저장소 쿼터

- 브랜치마다 데이터베이스 스토리지 쿼터가 있습니다. 요청으로 조정할 수 있습니다.
- 쿼터에 집계되는 것은 실제 데이터(테이블, 인덱스)입니다. 포인트인타임 복구용 기록은 집계되지 않습니다.
- 쿼터에 도달하면 쓰기 성능이 떨어집니다. 데이터를 지우면 공간을 회수할 수 있습니다.
- 컴퓨트는 시작하거나 재시작할 때 현재 쿼터를 읽습니다. 이미 실행 중인 컴퓨트는 재시작 전까지 이전 쿼터를 씁니다(Azure 문서).

### 3.2 기록 보존 기간 (History window)

| 항목 | 값 |
|---|---|
| 범위 | 2일 ~ 30일 |
| 기본값 | 7일 |
| 적용 범위 | 프로젝트의 모든 루트 브랜치 |
| 비용 영향 | 보존 기간을 늘리면 스토리지가 늘어남 |

포인트인타임 복구와 "과거 시점 쿼리(point-in-time branching)"에 쓰이는 기간입니다. 필요 이상으로 늘리지 않는 것이 비용 측면에서 유리합니다.

### 3.3 포인트인타임 복구 절차

문서 기준 절차는 다음과 같습니다. 이 절차는 **UI 흐름만** 문서에 있습니다. CLI나 API 명령은 근거 문서에서 확인하지 못했습니다.

1. Lakebase 앱에서 프로젝트를 열고 사이드바의 **Backup & Restore** 를 선택합니다.
2. **Restore from history** 에서 원본 브랜치와 날짜·시각을 고릅니다. **Preview data** 로 미리 볼 수 있습니다.
3. **Restore** 를 클릭하고 확인 화면에서 한 번 더 **Restore** 를 클릭합니다.

복구 결과는 **새 루트 브랜치** 입니다. 원래 브랜치는 바뀌지 않으며, 원래 연결은 계속 동작합니다. 복구된 데이터를 쓰려면 애플리케이션의 연결 설정을 새 브랜치로 바꿔야 합니다.

> **주의** 복구는 해당 브랜치의 **모든 Postgres 데이터베이스** 를 그 시점으로 되돌린 새 브랜치를 만듭니다. 문제가 된 데이터베이스 하나만 원하더라도 전체가 포함됩니다.

> **주의** 프로젝트에는 루트 브랜치가 최대 3개입니다. 복구 전에 쓰지 않는 루트 브랜치를 삭제해야 할 수 있습니다.

> **참고** 복구된 루트 브랜치에는 스냅샷 일정을 설정할 수 있다고 문서가 설명합니다. 수동 스냅샷은 프로젝트당 최대 10개입니다.

## 4. 과금 구조 (문서에 명시된 범위)

### 4.1 확인된 과금 메커니즘

| 항목 | 문서가 설명하는 내용 |
|---|---|
| 서버리스 사용 정책 | 프로젝트에 **serverless usage policy** 를 연결하면 서버리스 컴퓨트 비용을 특정 정책에 귀속시킴 |
| 사용자 태그 | 프로젝트의 사용자 정의 태그는 계정의 청구 가능 사용 기록(`system.billing.usage`)에 기록됨. 팀, 프로젝트, 비용 센터별 추적에 사용 |
| 태그 갱신 | API나 CLI로 태그를 갱신하면 기존 태그 목록 전체가 교체됨 |
| 스토리지 | 기록 보존 기간 연장은 스토리지를 늘림 |
| 스토리지 쿼터 | 포인트인타임 복구 기록은 쿼터에 집계되지 않음 |
| 브랜치 (만료 설정) | 만료 설정 브랜치는 **바뀐 데이터** 만 과금 |
| 브랜치 (영구) | 만료가 없는 브랜치는 **데이터 전체 크기** 로 과금 |
| 스케일 투 제로 | 비활성 컴퓨트를 일시 중지해 활성 컴퓨트 한도를 지키는 용도로 설명. 일시 중지 상태의 과금 여부는 문서에 명시 없음 |

### 4.2 문서에 명시되지 않은 것

- 과금 단위(DBU 등)와 단가는 이 장의 근거 문서에 없습니다.
- 컴퓨트 과금이 CU 단위로 계산되는지, 시간 단위인지 원문에서 확인하지 못했습니다.
- 동기화 테이블과 CDF의 과금은 문서에 명시가 없습니다. 동기화 테이블은 비용 구조의 상대 설명(Continuous가 가장 비싸다 등)만 있습니다.

### 4.3 비용 확인 방법

1. 공식 pricing 페이지에서 Lakebase 항목의 과금 단위와 단가를 확인합니다. 이 장 작성 시점에 Lakebase pricing 페이지는 요금 표가 렌더링되지 않았고, "Pay as you go with a 14-day free trial"과 약정 할인 문의 안내만 확인했습니다.
2. 워크스페이스의 `system.billing.usage` 테이블에서 프로젝트 태그로 실제 사용량을 집계합니다.
3. 견적은 확인한 단가와 과금 단위를 함께 적고, 기준일을 명시하십시오.

> **주의** 이 페이지에는 단가 숫자를 쓰지 않았습니다. 단가는 공식 pricing 페이지에서 직접 확인한 뒤 견적에 넣으십시오.

## 5. 비용을 줄이는 설정 체크리스트

| 점검 항목 | 확인 방법 |
|---|---|
| 쓰지 않는 개발 브랜치 삭제 또는 만료 설정 | 브랜치 목록에서 만료 여부 확인 |
| 유휴 컴퓨트의 스케일 투 제로 활성화 | 컴퓨트 설정 확인 |
| 기록 보존 기간을 필요한 만큼만 설정 | 프로젝트 설정의 History window |
| 영구 브랜치 최소화 | 브랜치 만료 설정 점검 |
| 동기화 테이블 모드 점검 | 변경률이 낮으면 Snapshot, 주기적 변경이면 Triggered, 실시간이 꼭 필요할 때만 Continuous |
| 프로젝트 태그로 비용 귀속 | 프로젝트 설정의 사용자 정의 태그 |
| 서버리스 사용 정책 연결 | 프로젝트 설정의 serverless usage policy |

## 6. 운영 기준

### 6.1 자동 업데이트 시간 설정

문서에 따르면 Lakebase는 Postgres 마이너 버전 업그레이드, 보안 패치, 플랫폼 기능을 예약 업데이트로 자동 적용합니다. 업데이트는 컴퓨트를 몇 초 동안 재시작합니다. 선호하는 요일과 시간을 설정하면 재시작은 그 시간대 안에서 일어납니다.

### 6.2 프로젝트 삭제 순서

1. 프로젝트를 삭제하면 7일 동안 소프트 삭제 상태로 보관되며, 그 동안 복구할 수 있습니다.
2. 문서는 프로젝트 삭제 전에 **연결된 Unity Catalog 카탈로그와 동기화 테이블을 먼저 삭제** 하라고 권장합니다. 그렇지 않으면 카탈로그를 조회하거나 SQL을 실행할 때 오류가 납니다.
3. 소유자가 아닌 테이블·카탈로그는 삭제 전에 본인에게 소유권을 넘겨야 합니다.
4. 즉시 완전 삭제는 `purge` 옵션을 씁니다. 이 옵션은 7일 보관을 건너뜁니다.

> **주의** 소프트 삭제 중에는 프로젝트에 연결을 시도하면 "엔드포인트 없음"이나 "연결 거부" 같은 일반 오류가 납니다. 프로젝트 삭제 상태를 바로 알 수 없으므로 `show_deleted=true`로 목록을 확인하십시오.

## 7. 체크리스트 요약

- [ ] 프로젝트·브랜치 구조를 격리 요구에 맞게 정했다.
- [ ] 컴퓨트 최소·최대 범위를 설정하고 스케일 투 제로 조건(최대 32 CU 이하)을 확인했다.
- [ ] 연결 방식(OAuth 또는 네이티브 비밀번호)과 풀링 여부를 함께 정했다.
- [ ] 토큰 재발급과 재연결 로직을 넣었다.
- [ ] 기록 보존 기간을 필요한 만큼 설정했다.
- [ ] 동기화 테이블 모드와 기본 키를 설계했다.
- [ ] CDF 또는 논리 복제의 상태 라벨과 제약을 확인했다.
- [ ] 과금 단위와 단가를 공식 pricing 페이지에서 확인해 견적에 기준일과 함께 적었다.
- [ ] 자동 업데이트 시간대를 운영 시간 밖으로 설정했다.
