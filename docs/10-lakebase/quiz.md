# 퀴즈와 체크리스트

이 장에서 다룬 내용을 확인하는 문제입니다. 정답을 펼치면 해설과 근거 페이지로 가는 링크가 있습니다.

## 퀴즈

### 1. Lakebase를 가장 정확히 설명한 것은? (수준 100)

- A. Delta 테이블을 저장하는 객체 스토리지 계층
- B. Databricks 플랫폼에 통합된 관리형 Postgres 데이터베이스
- C. Spark 클러스터에서 Postgres 쿼리를 실행하는 엔진
- D. 외부 Postgres의 변경을 Delta로만 옮기는 복제 도구

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 개요 페이지는 Lakebase를 "fully managed Postgres database integrated into the Databricks platform"으로 설명합니다. A는 Delta 저장소가 아니며, Delta 테이블은 동기화 테이블의 원본으로 등장합니다. C는 쿼리를 Postgres 엔진이 실행한다는 본문과 다릅니다. D는 변경 데이터 반출의 한 기능(CDF 또는 논리 복제)을 설명한 것이지 Lakebase의 정의가 아닙니다.

근거: [Lakebase 개요 — 한눈에 보기](what-is-lakebase.md#한눈에-보기)

</details>

### 2. 새 브랜치를 만들었을 때 본문이 설명하는 동작은? (수준 100)

- A. 부모의 데이터를 전부 복사하므로 데이터 크기만큼 생성 시간이 걸린다
- B. 부모의 스키마와 데이터를 상속하고 스토리지를 공유하며, 바뀐 부분만 따로 저장된다
- C. 부모의 변경이 자식에 자동으로 반영되어 항상 같은 상태를 유지한다
- D. 역할과 GRANT는 부모와 공유되므로 한 브랜치에서 바꾸면 모든 브랜치에 적용된다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 브랜치는 copy-on-write 방식으로 만들어지며, 부모의 스키마와 데이터를 상속하고 스토리지를 공유합니다. 생성 시간은 데이터베이스 크기와 무관합니다. 부모의 변경은 자식에 자동으로 반영되지 않고, 역할과 GRANT/REVOKE는 브랜치마다 격리됩니다(A, C, D는 모두 본문과 반대).

근거: [브랜치와 복구 — 2.1 동작 원리](branches-and-recovery.md#21-동작-원리)

</details>

### 3. 컴퓨트를 일시 중지해도 데이터가 남는 이유로 본문이 설명하는 것은? (수준 100)

- A. 컴퓨트가 매번 데이터를 Delta 테이블에 백업하기 때문
- B. 커넥션 풀이 데이터를 메모리에 보관하기 때문
- C. 데이터가 컴퓨트와 분리된 내구성 있는 스토리지 계층에 있기 때문
- D. 일시 중지 상태에서는 데이터가 다른 리전으로 옮겨지기 때문

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — 본문은 상태가 없는 Postgres 컴퓨트와 내구성 있는 스토리지 계층을 분리한다고 설명합니다. 스토리지는 컴퓨트가 실행 중이든 일시 중지되었든 데이터를 유지합니다. 컴퓨트를 재시작하면 연결은 끊기므로 애플리케이션에는 재연결 로직이 필요합니다.

근거: [Lakebase 개요 — 스토리지와 컴퓨트 분리](what-is-lakebase.md#스토리지와-컴퓨트-분리)

</details>

### 4. OAuth 토큰으로 인증하는 서비스가 내장 연결 풀러를 쓰려고 합니다. 옳은 판단은? (수준 200)

- A. 호스트에 풀러 스위치만 켜면 OAuth 토큰을 그대로 쓸 수 있다
- B. 풀러는 네이티브 Postgres 비밀번호 역할만 받으므로, OAuth를 쓰는 서비스는 앱 측 풀을 직접 연결 앞에 두는 구성을 검토한다
- C. 풀러를 쓰면 토큰 만료 검사가 생략되므로 OAuth와 함께 쓰기 좋다
- D. 풀러는 읽기 전용 컴퓨트에서만 쓸 수 있어 OAuth 서비스와 무관하다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 연결 풀링 페이지는 풀러가 네이티브 비밀번호 역할만 받으며, OAuth 역할을 고르면 풀러 스위치가 보이지 않는다고 설명합니다. 풀러와 OAuth는 배타 관계이므로 인증 방식과 풀링 방식을 설계 초기에 함께 정하라고 권장합니다. C는 두 기능이 배타적이라는 본문과 다르고, D는 풀러가 읽기-쓰기와 읽기 전용 호스트 모두에서 쓰인다는 본문과 다릅니다.

근거: [커넥션 풀링 — 2.4 인증 요건](connection-pooling.md#24-인증-요건)

</details>

### 5. 레이크하우스 테이블을 Lakebase로 동기화하는데, 한 주기에 원본 행의 대부분이 바뀝니다. 가장 적합한 모드는? (수준 200)

- A. Continuous: 지연이 가장 짧으므로 항상 우선 선택한다
- B. Snapshot: 변경 비율이 높을 때 전체를 다시 복사하는 방식이 효율적이다
- C. Triggered: 짧은 간격으로 자주 실행하면 가장 저렴하다
- D. 모드와 무관하게 Postgres에서 직접 써서 갱신한다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 원본의 변경 비율이 높을 때 Snapshot이 효율적이라고 설명합니다. Continuous는 지연은 가장 낮지만 비용은 가장 높습니다. Triggered를 짧은 간격으로 돌리면 비싸다고 본문이 설명하므로 C는 틀립니다. 동기화 테이블은 Postgres에서 직접 쓰기보다 원본 쪽에서 변경하라고 권장합니다.

근거: [동기화 테이블 — 동기화 모드](synced-tables.md#동기화-모드)

</details>

### 6. Databricks Apps에 Lakebase 데이터베이스를 리소스로 바인딩했습니다. 본문이 설명하는 주입 방식으로 옳은 것은? (수준 200)

- A. 비밀번호와 토큰 변수가 함께 주입되므로 코드에 연결 정보를 넣을 필요가 없다
- B. PGHOST, PGDATABASE, PGUSER 등 연결 관련 환경 변수가 주입되지만, 나열된 목록에는 비밀번호나 토큰 변수가 없다
- C. 엔드포인트 경로까지 환경 변수로 자동 주입된다
- D. 여러 데이터베이스를 바인딩하면 모든 연결 정보가 환경 변수로 주입된다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문이 나열한 환경 변수는 PGAPPNAME, PGDATABASE, PGHOST, PGPORT, PGSSLMODE, PGUSER입니다. 비밀번호와 토큰 변수는 목록에 없으며, 엔드포인트 경로도 주입되지 않습니다(C 틀림). 환경 변수는 첫 번째 데이터베이스 리소스만 반영되므로 D도 틀립니다.

근거: [Databricks Apps와 함께 쓰기 — 4. 주입되는 환경 변수](apps-integration.md#4-주입되는-환경-변수)

</details>

### 7. 풀러를 거치는 환경에서 설정을 모든 세션에 유지하려면 어떻게 해야 합니까? (수준 200)

- A. 트랜잭션 안에서 SET 명령을 실행한다
- B. 트랜잭션 밖에서 SET을 한 번 실행하면 이후 연결에도 남는다
- C. 역할 단위로 ALTER ROLE ... SET을 사용한다
- D. 풀러 스위치를 끄고 SET 명령을 요청마다 반복 실행한다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — 트랜잭션 모드 풀에서는 SET으로 바꾼 설정이 트랜잭션이 끝나면 사라집니다. 본문 예시에서도 COMMIT 뒤의 다른 트랜잭션은 SET 결과를 이어받지 못합니다. 역할 단위 설정(ALTER ROLE ... SET)은 연결이 바뀌어도 유지됩니다. B와 D는 트랜잭션 밖의 SET이 다음 요청에 남지 않는다는 본문과 어긋납니다.

근거: [커넥션 풀링 — 3.3 세션 설정을 유지하는 방법](connection-pooling.md#33-세션-설정을-유지하는-방법)

</details>

### 8. 쓰기 직후 바로 읽어야 하는 주문 조회 API가 있습니다. 읽기 복제본을 조회 트래픽에 쓰려고 합니다. 가장 적절한 판단은? (수준 300)

- A. 복제본은 동기 복제라 쓰기 직후에도 최신 값을 보장하므로 그대로 써도 된다
- B. 복제는 비동기라 방금 커밋된 값이 복제본에 아직 보이지 않을 수 있으므로, 쓰기 직후 읽기는 주 컴퓨트로 보낸다
- C. 복제본은 HA 보조 컴퓨트와 같은 역할이어서 장애가 났을 때만 읽을 수 있다
- D. 복제본은 별도 데이터 사본이므로 주 컴퓨트의 쓰기와 무관하다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 읽기 복제본은 주 컴퓨트와 같은 스토리지를 읽는 독립된 읽기 전용 컴퓨트이며, 복제는 비동기로 최종 일관성(eventually consistent)을 가집니다. 문서는 방금 쓴 값을 바로 읽어야 하는 요청을 주 컴퓨트로 보내라고 권장합니다. C는 HA 보조 컴퓨트와 읽기 복제본을 혼동한 것이고, D는 복제본이 데이터 사본을 따로 만들지 않는다는 본문과 반대입니다.

근거: [컴퓨트와 스케일링 — 2.3 읽기 복제본 (Read replica)](compute-and-scaling.md#23-읽기-복제본-read-replica)

</details>

### 9. 운영 프로젝트에 고가용성(HA) 구성을 적용하려고 합니다. 스케일 투 제로와의 관계로 옳은 것은? (수준 300)

- A. HA와 스케일 투 제로를 함께 켜면 유휴 상태에서 보조 컴퓨트만 멈춘다
- B. HA를 켜려면 스케일 투 제로를 꺼야 하며, 같은 엔드포인트에서 두 기능을 함께 쓸 수 없다
- C. 보조 컴퓨트를 하나라도 두면 스케일 투 제로가 자동으로 적용된다
- D. 스케일 투 제로 제한은 읽기 복제본에만 해당하고 HA와는 무관하다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 컴퓨트 페이지는 HA 활성화의 전제로 스케일 투 제로를 꺼야 한다고 명시합니다. 트레이드오프 표도 HA는 스케일 투 제로 불가, 스케일 투 제로는 장애 대응이 필요 없는 개발 브랜치에 맞는다고 정리합니다. 따라서 장애 조치가 필요한 운영 엔드포인트는 상시 가동 비용을 받아들이는 설계가 됩니다.

근거: [컴퓨트와 스케일링 — 2.4 고가용성 (High availability, HA)](compute-and-scaling.md#24-고가용성-high-availability-ha)

</details>

### 10. Lakebase 테이블의 변경 이력을 Delta로 남기는 CDF를 설계합니다. 본문이 설명하는 설계 조건은? (수준 300)

- A. 대상 Delta 테이블에도 Delta 변경 데이터 피드를 함께 켠다
- B. 대상 Delta 테이블에 행 필터와 열 마스크를 걸어 보안을 강화한다
- C. 원본 테이블을 REPLICA IDENTITY FULL로 설정해야 수정·삭제 이전 값이 로그에 남아 이력이 완전해진다
- D. 파티션 테이블도 제약 없이 피드에 포함된다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — CDF가 테이블을 포함하려면 REPLICA IDENTITY FULL이어야 하며, 설정하지 않으면 로그에 기본 키만 남습니다. 본문은 대상 Delta 테이블에 Delta 변경 데이터 피드를 켜지 말라고 경고하고(A 틀림), 행 필터나 열 마스크를 걸면 CDF가 쓰기를 멈춘다고 설명합니다(B 틀림). 파티션 테이블은 지원되지 않습니다(D 틀림).

근거: [변경 데이터 반출 — 2.4 설정 방법](change-data-out.md#24-설정-방법), [변경 데이터 반출 — 2.5 제약과 주의](change-data-out.md#25-제약과-주의)

</details>
