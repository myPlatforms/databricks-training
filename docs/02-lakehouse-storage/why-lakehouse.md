# 레이크하우스가 필요한 이유

> 기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 100

레이크하우스(Lakehouse)는 데이터 레이크의 저렴한 저장소와 데이터 웨어하우스의 관리 기능을 한 곳에 합친 데이터 관리 구조입니다. 공식 문서는 데이터 레이크하우스를 "데이터 레이크와 데이터 웨어하우스의 장점을 결합한 데이터 관리 시스템"으로 정의합니다. 이 페이지는 두 기존 구조가 왜 한계에 부딪혔는지, 레이크하우스가 그 사이에서 무엇을 해결하는지 설명합니다.

## 1. 왜 필요한가

### 데이터 웨어하우스의 한계

데이터 웨어하우스는 BI 쿼리에 최적화된 구조입니다. 스키마가 고정되어 있고 트랜잭션이 보장되므로 리포트의 정확성은 높습니다. 대신 다음과 같은 문제가 있습니다.

| 문제 | 설명 |
|---|---|
| 독점 포맷 | 데이터가 벤더 고유 포맷으로 저장되어 다른 엔진이 직접 읽기 어렵습니다 |
| 비정형 데이터 취급 | 로그, 이미지, 텍스트 같은 데이터를 다루기 불편하고 비쌉니다 |
| 머신러닝 지원 제한 | 학습 데이터를 웨어하우스 밖으로 꺼내 다시 가공해야 하는 경우가 많습니다 |
| 비용 구조 | 저장과 컴퓨트가 강하게 묶여 있어 원본 데이터를 많이 쌓아 두기 어렵습니다 |

공식 문서는 웨어하우스를 BI 쿼리에 적합하지만 느려질 수 있고, 독점 포맷 때문에 머신러닝 지원이 제한된다고 설명합니다.

### 데이터 레이크의 한계

데이터 레이크는 오브젝트 스토리지(예: Amazon S3)에 원본 파일을 그대로 두는 방식입니다. 저렴하고 포맷 제약이 없지만, 파일을 쌓기만 하면 다음 문제가 생깁니다.

| 문제 | 설명 |
|---|---|
| 트랜잭션 부재 | 쓰기 도중 실패하면 일부 파일만 남아 테이블이 깨진 상태가 됩니다 |
| 읽기 일관성 부재 | 쓰기와 읽기가 동시에 일어나면 반쯤 쓰인 데이터를 읽을 수 있습니다 |
| 스키마 관리 부재 | 파일마다 컬럼이 달라져도 감지되지 않고, 나중에 쿼리가 깨집니다 |
| 수정·삭제 비용 | 행 하나를 바꾸려면 파일을 통째로 다시 써야 합니다 |
| 거버넌스 분산 | 파일 경로에 권한을 거는 방식이라 테이블·컬럼 단위 통제가 어렵습니다 |

> **주의** 데이터 레이크의 "스키마 부재"는 파일 포맷 자체의 문제가 아니라 관리 계층이 없어서 생기는 문제입니다. Parquet 파일만으로는 트랜잭션과 버전 이력을 보장할 수 없습니다.

### 레이크하우스가 해결하는 것

레이크하우스는 두 가지를 동시에 목표로 합니다.

1. **열린 포맷의 파일을 그대로 둔다.** 데이터는 오브젝트 스토리지에 Parquet 기반 파일로 남고, 외부 엔진도 읽을 수 있습니다.
2. **그 위에 테이블 계층을 얹는다.** 트랜잭션 로그, 스키마 검증, 버전 이력, 파일 최적화, 권한 모델을 테이블 단위로 제공합니다.

Databricks에서 이 계층의 기본은 Delta Lake이고, 여러 엔진과의 상호 운용을 위해 Apache Iceberg도 지원합니다. 두 포맷과 Unity Catalog의 관계는 [Delta Lake 동작 원리](delta-lake-internals.md)와 [Apache Iceberg 지원](iceberg-support.md)에서 자세히 다룹니다.

| 요구 | 웨어하우스 | 데이터 레이크 | 레이크하우스 |
|---|---|---|---|
| BI 쿼리 성능 | 높음 | 낮음 | 테이블 최적화로 확보 |
| 열린 포맷 | 보통은 아님 | 열림 | 열림 (Delta, Iceberg) |
| 트랜잭션 | 있음 | 없음 | 있음 |
| 스키마 강제 | 있음 | 없음 | 있음 (쓰기 시 검증) |
| 비정형·ML 데이터 | 제한적 | 적합 | 적합 |
| 저장 비용 | 높은 편 | 낮음 | 낮음 (오브젝트 스토리지) |

## 2. 어떻게 동작하는가

레이크하우스의 핵심 구성 요소는 다음 네 가지입니다.

| 구성 요소 | 역할 | 이 장에서 다루는 페이지 |
|---|---|---|
| 오픈 파일 포맷 | 데이터 파일(Parquet)을 오브젝트 스토리지에 저장 | Delta Lake 동작 원리 |
| 테이블 메타데이터 계층 | 트랜잭션 로그(Delta) 또는 Iceberg 메타데이터 파일이 어떤 파일이 현재 버전에 속하는지 기록 | Delta Lake 동작 원리, Apache Iceberg 지원 |
| 카탈로그와 거버넌스 | 테이블 이름, 권한, 리니지를 관리 | 관리형 vs 외부 테이블 |
| 컴퓨트 엔진 | Spark, SQL 웨어하우스 등이 같은 테이블을 읽고 씀 | 각 페이지의 SQL 예시 |

공식 문서의 "What is Delta Lake" 페이지는 Delta Lake가 Parquet 데이터 파일에 파일 기반 트랜잭션 로그를 덧붙여 ACID 트랜잭션과 확장 가능한 메타데이터 처리를 제공한다고 설명합니다. 이 로그는 누구나 읽을 수 있는 공개 프로토콜을 따릅니다.

일반적인 데이터 흐름은 다음 표처럼 정리할 수 있습니다.

| 단계 | 작업 | 레이크하우스에서의 처리 |
|---|---|---|
| 수집 | 원본 파일, 스트림, 외부 DB 적재 | 원본을 그대로 테이블에 적재 (브론즈) |
| 정제 | 중복 제거, 타입 정리, 검증 | 검증된 테이블 생성 (실버) |
| 서빙 | BI, 대시보드, ML 피처 | 집계·비즈니스 뷰 제공 (골드) |

계층 구분의 기준은 [메달리온 아키텍처](medallion-architecture.md)에서 다룹니다.

## 3. 어떻게 쓰는가

레이크하우스 테이블은 SQL 한 줄로 만들 수 있습니다. 다음은 Unity Catalog 관리형 Delta 테이블을 만드는 예시입니다. 기본 테이블 형식은 Delta Lake이므로 `USING` 절을 생략해도 Delta 테이블이 됩니다.

```sql
CREATE TABLE main.sales.orders (
  order_id   BIGINT,
  customer   STRING,
  amount     DECIMAL(12, 2),
  order_ts   TIMESTAMP
);
```

같은 데이터를 여러 엔진이 읽어야 한다면 Iceberg 형식을 명시할 수 있습니다.

```sql
CREATE TABLE main.sales.orders_iceberg (
  order_id   BIGINT,
  customer   STRING,
  amount     DECIMAL(12, 2),
  order_ts   TIMESTAMP
) USING ICEBERG;
```

> **참고** 위 예시의 `main` 카탈로그와 `sales` 스키마는 예시 이름입니다. 실제 실행 전 본인 워크스페이스의 카탈로그와 스키마에 `CREATE TABLE` 권한이 있는지 확인하십시오.

Iceberg 관리형 테이블의 구체적인 문법과 제약은 [Apache Iceberg 지원](iceberg-support.md)에서 설명합니다.

## 4. 트레이드오프

| 항목 | 장점 | 비용·제약 |
|---|---|---|
| 저장 | 오브젝트 스토리지 가격으로 원본 보관 가능 | 버전 이력(타임 트래블)을 길게 두면 파일이 누적되어 저장 비용이 늘어납니다 |
| 쓰기 | 트랜잭션으로 부분 쓰기가 보이지 않음 | 작은 파일이 많이 쌓이면 읽기가 느려지므로 주기적 최적화가 필요합니다 |
| 호환성 | 열린 포맷으로 여러 엔진이 읽음 | 엔진마다 지원하는 기능 범위가 다르므로 기능 조합을 확인해야 합니다 |
| 거버넌스 | 테이블·컬럼 단위 권한 | 외부 경로로 직접 접근하면 Unity Catalog 권한이 적용되지 않습니다 (관리형 vs 외부 테이블 페이지 참고) |
| 운영 | 최적화를 자동화할 수 있음 | 자동화 설정(예측 최적화)의 가용 조건을 확인해야 합니다 |

### 언제 레이크하우스 구조가 맞지 않는가

- 트랜잭션 단위가 밀리초 단위의 행 조회·수정인 애플리케이션 백엔드라면 OLTP 데이터베이스가 더 적합할 수 있습니다. 이 경우 [Lakebase](../10-lakebase/what-is-lakebase.md)를 함께 검토할 수 있습니다.
- 데이터가 작고 단일 BI 도구만 쓰는 경우에는 레이크하우스 구성이 과할 수 있습니다.

## 5. 주의사항

> **주의** "레이크하우스를 쓰면 웨어하우스가 필요 없다"는 뜻이 아닙니다. 공식 문서는 레이크하우스를 두 구조의 장점을 결합한 구조로 설명하며, 서빙 계층 설계는 여전히 필요합니다.

> **주의** 레이크하우스의 열린 포맷은 "어디서든 아무 도구로 쓰기"를 보장하지 않습니다. 외부 클라이언트의 쓰기 지원 범위는 테이블 유형과 카탈로그 설정에 따라 다르므로 [관리형 vs 외부 테이블](managed-vs-external-tables.md)과 [Apache Iceberg 지원](iceberg-support.md)을 함께 확인하십시오.

- 쓰기 경로를 여러 개(노트북, 외부 Spark 잡, 파일 직접 복사)로 나누면 테이블 상태가 예측하기 어려워집니다. 쓰기 주체를 파이프라인으로 모으는 것을 권장합니다.
- 처음부터 모든 데이터를 같은 포맷으로 묶으려 하지 마십시오. 계층별로 필요한 포맷과 보존 기간을 정하는 것이 운영 부담을 줄입니다.
