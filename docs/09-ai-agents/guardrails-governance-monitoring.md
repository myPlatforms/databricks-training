# 가드레일·거버넌스·모니터링

> 기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 300

## 왜 필요한가

에이전트는 사용자 입력을 받아 모델에 보내고, 도구를 호출하고, 결과를 사용자에게 돌려줍니다. 이 경로 어디에서든 문제가 생길 수 있습니다. 사용자가 개인정보를 입력하거나, 프롬프트 인젝션으로 도구 호출을 조작하거나, 모델이 부적절한 응답을 내거나, 한 사용자가 예산을 모두 쓰는 상황입니다.

가드레일(Guardrail)은 요청과 응답의 내용을 검사해 허용 여부를 정하는 장치입니다. 거버넌스는 누가 어떤 모델과 도구를 쓸 수 있는지, 얼마나 쓸 수 있는지, 무엇이 기록되는지를 정하는 장치입니다. 모니터링은 배포 후 상태를 보는 장치입니다. 세 가지는 서로 다른 질문에 답하므로 따로 설계합니다.

## 어떻게 동작하는가

Databricks 공식 문서의 AI 거버넌스 페이지는 다음 기능을 나열합니다. 상태 라벨은 원문 그대로 적었습니다.

| 기능 (문서 명칭) | 상태 라벨 | 역할 |
|---|---|---|
| 서비스 정책 (Service policies) | Beta | 내용에 따라 요청과 응답을 허용하거나 차단 |
| 내장 서비스 정책 (가드레일) | Beta (서비스 정책의 일부) | PII, 프롬프트 인젝션, 안전하지 않은 콘텐츠 등 위험 항목 검사 |
| 외부 서비스 정책 | Beta (서비스 정책의 일부) | 제3자 가드레일 제공자의 판정을 적용 |
| 속도 제한과 지출 상한 | 문서에 명시 없음 | 모델과 MCP 서비스의 용량 보호, 비용 통제 |
| 사용량 추적 | 문서에 명시 없음 | 누가 어떤 모델이나 MCP 서비스를 언제 호출했는지 기록 |
| 비용 관찰 | 문서에 명시 없음 | 모델, 프린시펄, 태그별 비용 분석 |
| 추론 테이블 (Inference tables) | 문서에 명시 없음 | 요청과 응답의 전체 페이로드 저장 |
| Unity Gateway | generally available | 트래픽 라우팅, 속도 제한, 사용량 추적을 담당 |
| Unity Catalog 자산 거버넌스 | generally available | 테이블, 함수, 볼륨 등의 권한과 정책 |

서비스 정책은 Unity Gateway의 **Service Policies** 프리뷰를 통해 접근합니다. 문서는 "Service policies are in Beta"라고 명시합니다.

서비스 정책은 MCP 서비스에 붙을 때 입력 정책으로 사람의 승인을 요구할 수도 있다고 문서에 적혀 있습니다.

> **참고** 이 페이지에서 확인하지 못한 항목은 다음과 같습니다. 별도의 안전 필터(safety filter) 기능, 독립된 PII 탐지 기능, 가드레일 실패 시 동작(fail-closed 여부). 문서는 PII를 위험 예시로만 언급하며, 실패 시 동작은 설명하지 않습니다. 이 장은 해당 내용을 쓰지 않았습니다.

## 어떻게 쓰는가

### 1. 권한으로 먼저 막기

가장 확실한 통제는 권한입니다. 도구와 모델의 접근은 Unity Catalog 권한과 Unity Gateway 정책으로 정합니다. 에이전트가 쓰는 함수, 테이블, MCP 서비스에 대해 필요한 사용자와 서비스 프린시펄에만 권한을 주십시오. 권한 모델은 06장의 [권한 모델과 소유권](../06-unity-catalog/privileges-and-ownership.md)과 [거버넌스 태그와 ABAC 정책](../06-unity-catalog/governed-tags-and-abac.md)에서 다룹니다.

MCP 서비스는 호출자별로 접근을 정합니다. 호출자는 MCP 호출을 위해 Consumer access가 있어야 하고, 서비스 자체에는 CAN USE 같은 권한이 필요합니다. 자세한 조건은 [도구: UC 함수와 MCP 서버](tools-uc-functions-and-mcp.md)과 [배포와 인증](deploy-and-authentication.md)에 있습니다.

### 2. 서비스 정책 설계

서비스 정책은 요청과 응답 내용을 기준으로 허용 또는 차단을 정합니다. 설계 순서는 다음과 같습니다.

1. 위험 항목을 정합니다. 개인정보 노출, 프롬프트 인젝션, 금지 콘텐츠 중 무엇을 막을지 목록으로 씁니다.
2. 내장 정책으로 충분한지 봅니다. 문서는 내장 정책이 PII, 프롬프트 인젝션, 안전하지 않은 콘텐츠 같은 위험을 다룬다고 설명합니다.
3. 제3자 가드레일을 이미 쓰는 조직이라면 외부 서비스 정책으로 그 판정을 적용할 수 있는지 봅니다.
4. 정책을 붙인 뒤 차단과 허용 결과를 어떤 기록으로 검토할지 정합니다. 정책 결정이 사용량 추적과 트레이스 중 어디에 남는지는 이 장의 원문 확인 범위에 없으므로, 적용 전에 서비스 정책 문서에서 확인하십시오.

문서 가이드에는 모델 서비스에 가드레일을 추가하는 튜토리얼(Tutorial: Add service policy guardrails to a model service)이 있습니다. 실제 설정 단계는 그 튜토리얼 원문을 따르십시오.

> **주의** 서비스 정책은 Beta입니다. 운영 에이전트의 필수 통제로 넣기 전에 상태와 지원 범위를 확인하십시오. 정책이 빠진 경로가 있는지도 확인하십시오. 예를 들어 워크스페이스 MCP 엔드포인트는 Unity Gateway의 거버넌스 대상이 아니라고 문서에 명시되어 있습니다([도구: UC 함수와 MCP 서버](tools-uc-functions-and-mcp.md) 참고).

### 3. 속도 제한과 지출 상한

속도 제한은 모델과 MCP 서비스의 호출량을 제한해 용량을 보호하고 비용을 통제합니다. 문서는 이 기능의 상태 라벨을 명시하지 않습니다. 설정 방법은 [속도 제한 적용](https://docs.databricks.com/aws/en/ai-gateway/rate-limits) 페이지에서 확인하십시오.

설계 기준은 다음과 같습니다.

- 대화형 에이전트는 사용자 단위 한도가 있어야 특정 사용자의 과도한 호출이 전체 서비스를 밀어내지 않습니다.
- 배치 작업으로 도는 에이전트는 작업 단위 한도를 따로 두는 편이 낫습니다.
- 한도에 걸린 요청이 어떤 응답으로 돌아가는지 테스트에서 확인하십시오.

### 4. 사용량 추적과 비용 관찰

사용량 추적은 누가 어떤 모델이나 MCP 서비스를 언제 호출했는지 기록합니다. 비용 관찰은 그 기록을 모델, 프린시펄, 태그 기준으로 분석합니다. 두 기능 모두 문서에 상태 라벨이 없습니다.

운영에서는 다음 질문에 답할 수 있어야 합니다.

| 질문 | 확인 수단 |
|---|---|
| 어떤 사용자가 에이전트를 얼마나 호출했는가 | 사용량 추적 |
| 비용이 어떤 모델과 팀에서 나오는가 | 비용 관찰 (태그 기준 분석) |
| 실제 질문과 응답 내용은 무엇이었는가 | 추론 테이블 (전체 페이로드) |
| 어떤 도구 호출이 실패했는가 | MLflow 트레이스 ([트레이싱·평가·피드백](tracing-evaluation-feedback.md)) |

### 5. 추론 테이블과 트레이스의 차이

추론 테이블은 요청과 응답의 **전체 페이로드** 를 저장합니다. MLflow 트레이스는 에이전트 실행의 **단계별 기록** 을 저장합니다. 목적이 다릅니다.

| 항목 | 추론 테이블 | MLflow 트레이스 |
|---|---|---|
| 기록 단위 | 모델 또는 MCP 요청과 응답 | 에이전트 한 번의 실행 (여러 단계) |
| 문서가 설명하는 내용 | 요청과 응답의 전체 페이로드 저장 | 단계별 실행 기록, 스코어러와 피드백 연결 |
| 주된 용도 (이 장의 설계 관점) | 감사, 재현 | 디버깅, 품질 평가 |

두 기록에는 민감한 내용이 들어 있으므로 접근 권한과 보존 기간을 함께 정하십시오.

## 모니터링

배포 후 품질은 MLflow 프로덕션 모니터링(Beta)으로 봅니다. 운영 트래픽의 일부에 스코어러를 돌리고 결과를 트레이스에 붙이는 방식입니다. 설정과 주의사항은 [트레이싱·평가·피드백](tracing-evaluation-feedback.md)에 있습니다.

모니터링은 품질만 보지 않습니다. 장애와 비용도 함께 봐야 합니다.

| 관찰 대상 | 기준 예시 | 수단 |
|---|---|---|
| 품질 | 스코어러 점수 추세 | 프로덕션 모니터링 |
| 도구 오류 | 도구 호출 실패율, 재시도 | 트레이스 |
| 사용량과 비용 | 호출 수, 사용자별 비용 | 사용량 추적, 비용 관찰 |
| 정책 결과 | 차단과 허용 건수 | 기록 위치는 서비스 정책 문서에서 확인 |

> **참고** 위 표의 "기준 예시"는 운영 설계를 위한 예시입니다. 문서가 특정 임계값을 제시하지 않습니다. 조직 기준으로 정하십시오.

## 트레이드오프

| 선택 | 장점 | 제약 |
|---|---|---|
| 권한으로 통제 | 가장 기본적이고 감사와 연결됨 | 내용 기반 차단은 못 함 |
| 서비스 정책 | 내용 기준의 허용 또는 차단 | Beta 상태 |
| 속도 제한 | 용량과 비용 통제 | 한도 도달 시 사용자 경험 저하 |
| 전체 페이로드 저장 | 감사와 재현에 유리 | 민감 정보 저장 부담, 비용 증가 |

## 주의사항

- **통제 계층을 섞지 않기**: 권한, 정책, 속도 제한은 서로 다른 문제를 풉니다. 한 계층으로 나머지를 대신하지 마십시오.
- **우회 경로 점검**: 같은 도구에 여러 경로가 있으면 모든 경로에 같은 통제를 거는지 확인하십시오. 워크스페이스 엔드포인트와 Unity Gateway 경로는 거버넌스 적용 범위가 다릅니다.
- **민감 정보 보존**: 추론 테이블과 트레이스에는 원문이 들어갑니다. 보존 기간과 접근 권한을 먼저 정하고, 고객 데이터를 다룬다면 해당 조직의 규정을 따르십시오.
- **상태 확인**: 서비스 정책, 프로덕션 모니터링, 리뷰 큐는 Beta입니다. 운영 필수 통제로 넣기 전에 확인하십시오.
- **가드레일의 한계**: 정책은 위험을 줄이지만 없애지는 못합니다. 권한 최소화와 사람 승인 절차를 함께 두십시오.
