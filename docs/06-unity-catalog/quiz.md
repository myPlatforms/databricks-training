# 퀴즈와 체크리스트

> 기준일: 2026-10-29 · 근거: 이 장 본문 · 수준: 100~300

이 장에서 다룬 내용을 확인하는 문제입니다. 정답을 펼치면 해설과 근거 페이지로 가는 링크가 있습니다.

## 퀴즈

### 1. Unity Catalog의 메타스토어(Metastore)를 가장 정확히 설명한 것은 무엇입니까? (수준 100)

- A. 워크스페이스 하나의 설정 파일 묶음
- B. 단일 클라우드 리전 안의 모든 Unity Catalog 객체를 담는 최상위 컨테이너
- C. 카탈로그 아래에 놓이는 스키마 묶음
- D. 클러스터 정책을 모아 둔 목록

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 메타스토어를 단일 클라우드 리전 안의 모든 Unity Catalog 객체를 담는 최상위 컨테이너로 설명합니다. 그래서 메타스토어는 리전 단위로 존재합니다. A, C, D는 메타스토어의 역할이 아닙니다. 스키마는 카탈로그 아래, 카탈로그는 메타스토어 아래에 놓입니다.

근거: [Unity Catalog 개요 — 메타스토어](what-is-unity-catalog.md#메타스토어)

</details>

### 2. Unity Catalog가 워크스페이스별 Hive 메타스토어 방식의 문제를 해결하는 방법은 무엇입니까? (수준 100)

- A. 모든 테이블을 파일 경로 기반으로 다시 저장한다
- B. 하나의 메타스토어와 하나의 권한 모델로 자산과 권한을 관리한다
- C. 워크스페이스마다 권한 정책을 따로 만들어 복제한다
- D. 노트북마다 스토리지 자격 증명을 직접 입력하게 한다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 UC가 이 문제를 하나의 메타스토어와 하나의 권한 모델로 해결한다고 설명합니다. 같은 메타스토어에 연결된 워크스페이스는 같은 자산 목록과 권한을 공유합니다. A, C, D는 본문이 문제로 든 방식이거나 UC의 해결책과 반대되는 방식입니다.

근거: [Unity Catalog 개요 — 왜 필요한가](what-is-unity-catalog.md#1-왜-필요한가)

</details>

### 3. 권한을 사용자 개인이 아니라 그룹에 주는 설계가 권장되는 가장 큰 이유는 무엇입니까? (수준 100)

- A. 그룹에 주면 권한 검사가 생략되어 빨라진다
- B. 사람이 바뀔 때마다 개별 GRANT를 고칠 필요가 줄어든다
- C. 그룹은 소유권을 가질 수 없으므로 안전하다
- D. 그룹 권한은 행 필터와 열 마스크를 자동으로 적용한다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 사용자마다 GRANT를 주면 인원이 바뀔 때마다 권한을 고쳐야 한다고 설명하고, 그래서 그룹을 권한 대상으로 쓰는 것을 기본 설계로 제시합니다. A는 권한 검사를 생략한다는 설명이 본문에 없으며, C는 그룹도 소유자가 될 수 있다는 본문 설명(소유권 이전 가능 주체)과 어긋납니다. D는 본문에 없는 동작입니다.

근거: [권한 모델과 소유권 — 그룹 중심 설계가 필요한 이유](privileges-and-ownership.md#그룹-중심-설계가-필요한-이유)

</details>

### 4. 테이블에 `SELECT` 권한만 부여하면 사용자가 테이블을 읽을 수 있습니까? (수준 200)

- A. 예. `SELECT`가 있으면 상위 객체의 권한은 필요하지 않다
- B. 아니요. 상위 카탈로그에 `USE CATALOG`, 상위 스키마에 `USE SCHEMA`도 있어야 한다
- C. 예. 단, 워크스페이스 관리자가 승인해야 한다
- D. 아니요. 테이블 소유자만 읽을 수 있다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 권한 참조 페이지는 사용자가 테이블에 `SELECT`를 가져도 상위 카탈로그에 `USE CATALOG`, 상위 스키마에 `USE SCHEMA`가 필요하다고 명시합니다. 이 두 권한은 진입 권한이며, 객체 데이터 접근 권한을 주지는 않습니다. 실무에서 `SELECT`만 주고 `USE SCHEMA`를 빠뜨리는 것이 흔한 실수입니다.

근거: [권한 모델과 소유권 — 필수 권한 조합](privileges-and-ownership.md#필수-권한-조합)

</details>

### 5. 외부 볼륨(External volume)에서 외부 시스템이 클라우드 스토리지 URI로 파일을 직접 읽으면 어떻게 됩니까? (수준 200)

- A. UC 권한이 그대로 적용되어 읽기가 막힌다
- B. UC 권한이 적용되지 않으므로 클라우드 측 접근 제어를 함께 설계해야 한다
- C. 볼륨을 삭제하면 자동으로 접근이 차단된다
- D. 관리형 볼륨으로 자동 전환되어 권한이 적용된다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 외부 볼륨에 대해 외부 시스템이 클라우드 URI로 직접 읽고 쓰면 UC 권한이 적용되지 않는다고 주의합니다. 그래서 자격 증명 벤딩이나 클라우드 네이티브 접근 제어를 함께 쓰라고 권장합니다. 외부 볼륨은 데이터를 복사하지 않고 기존 스토리지 경로를 가리키므로, 볼륨 삭제가 접근 차단을 뜻하지도 않습니다.

근거: [볼륨과 외부 스토리지 — 관리형 볼륨과 외부 볼륨](volumes-and-storage.md#관리형-볼륨과-외부-볼륨)

</details>

### 6. 새 테이블이 계속 생길 때 같은 행 필터·열 마스크 규칙을 자동으로 적용하려면 무엇이 더 적합합니까? (수준 200)

- A. 테이블마다 `ALTER TABLE ... SET ROW FILTER`를 반복한다
- B. 원본 테이블을 복사해 테이블별로 뷰를 만든다
- C. 태그 조건으로 대상을 고르는 ABAC 정책을 쓴다
- D. 노트북마다 필터 조건을 코드로 넣는다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — 본문은 테이블 단위 방식은 새 테이블마다 붙이기 전까지 노출되지만, ABAC 정책은 태그 조건만 맞으면 자동으로 적용된다고 비교합니다. 공식 권장도 중앙 관리와 확장이 필요하면 ABAC를 쓰고, 테이블 고유 로직이 필요하거나 ABAC를 아직 도입하지 않았을 때 테이블 단위 방식을 쓰라는 것입니다.

근거: [행 필터와 열 마스크 — ABAC 정책 방식](row-filters-and-column-masks.md#abac-정책-방식)

</details>

### 7. 테이블의 열이나 이름을 바꾸었을 때 데이터 계보(Lineage)에 대해 본문이 설명하는 내용은 무엇입니까? (수준 200)

- A. 이름 변경 이전의 계보까지 새 이름에 자동으로 이어진다
- B. 계보 그래프는 이름 변경 후에도 항상 같은 노드로 유지된다
- C. 이름을 바꾸면 계보가 이어지지 않는다고 한계로 명시되어 있다
- D. 이름 변경은 계보 시스템 테이블에만 영향을 준다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — 계보의 한계 표는 카탈로그, 스키마, 테이블, 뷰, 열의 이름을 바꾸면 계보가 이어지지 않는다고 명시하며, 주의사항에서도 이름 변경 계획을 따로 세우라고 권장합니다. A와 B는 본문과 반대되는 설명입니다. D는 계보 그래프 자체의 연속성이 끊긴다는 본문 설명과 맞지 않습니다.

근거: [계보와 데이터 분류 — 계보의 한계](lineage-and-classification.md#계보의-한계)

</details>

### 8. 태그 기반 GRANT 정책으로 받은 권한이 `SHOW GRANTS` 결과에 나타나는지에 대해 본문이 설명하는 내용은 무엇입니까? (수준 300)

- A. 항상 나타나므로 별도 점검이 필요 없다
- B. 나타나지 않으므로, 권한 점검 시 정책 목록도 함께 확인해야 한다
- C. 나타나지만 `MANAGE` 권한이 있을 때만 보인다
- D. 모델에서만 나타나고 다른 서비스에서는 나타나지 않는다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 GRANT 정책으로 받은 권한은 `SHOW GRANTS`에 나오지 않는다고 명시합니다. 따라서 권한 감사를 `SHOW GRANTS`만으로 하면 정책으로 준 권한이 빠집니다. C와 D는 본문에 없는 설명이며, A는 본문과 반대입니다.

근거: [거버넌스 태그와 ABAC 정책 — 정책 설계 예 (GRANT 정책)](governed-tags-and-abac.md#정책-설계-예-grant-정책)

</details>

### 9. 거버넌스 태그를 정책 조건에 쓰면서 태그 키를 `pii`에서 `PII`로 잘못 적었습니다. 본문이 경고하는 결과는 무엇입니까? (수준 300)

- A. 태그 키가 자동으로 소문자로 바뀌어 정책이 그대로 동작한다
- B. 정책 생성이 항상 실패하므로 바로 알 수 있다
- C. 정책이 대상을 찾지 못해 조용히 적용되지 않을 수 있다
- D. 같은 태그가 모든 객체에 자동으로 복제된다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: C** — 본문은 태그 키와 값이 대소문자를 구분하며, 오타가 있으면 정책이 대상을 찾지 못해 조용히 적용되지 않을 수 있다고 경고합니다. 그래서 정책 적용 결과를 테스트 계정으로 확인하라고 권장합니다. A와 D는 본문에 없는 동작이며, B처럼 항상 즉시 실패한다는 설명도 본문과 다릅니다.

근거: [거버넌스 태그와 ABAC 정책 — 주의사항](governed-tags-and-abac.md#5-주의사항)

</details>

### 10. 권한을 줄이거나 공유를 회수하기 전에 가장 먼저 해야 할 일은 무엇입니까? (수준 300)

- A. 회수 명령을 실행한 뒤 실패 로그를 보고 되돌린다
- B. 같은 권한으로 실행되는 소비자(노트북, 잡, 대시보드, Genie 공간, 다른 리포의 코드)를 확인한다
- C. 권한 범위를 요청보다 넓게 줄여 한 번에 정리한다
- D. 리시피언트에게 공유를 먼저 삭제하라고 요청한다

<details markdown="1">
<summary>정답과 해설</summary>

**정답: B** — 본문은 권한을 줄이면 그 권한을 쓰던 소비자가 조용히 실패하고 원인을 찾기 어렵다고 경고합니다. 그래서 회수 전에 소비자와 실행 주체를 먼저 확인하라고 권장합니다. 요청 범위를 넘는 축소는 선택지로만 제시하고 소비자 확인 없이 실행하지 말라고도 합니다. A는 장애가 뒤늦게 드러나는 방식이므로 본문이 피하라고 한 절차입니다.

근거: [베스트 프랙티스와 한도 — 권한 회수 전 점검](best-practices-and-limits.md#5-권한-회수-전-점검)

</details>

## 실무 체크리스트

이 장의 내용을 실제 환경에 적용할 때 확인할 항목입니다.

- [ ] 카탈로그와 스키마 경계를 환경, 팀, 사업부 기준으로 정했다 — [베스트 프랙티스와 한도](best-practices-and-limits.md#1-설계-원칙)
- [ ] 권한은 그룹에 주고, 운영 카탈로그와 스키마의 소유자도 그룹으로 두었다 — [권한 모델과 소유권](privileges-and-ownership.md#소유권)
- [ ] `GRANT`할 때 `USE CATALOG`와 `USE SCHEMA` 진입 권한을 함께 주었다 — [권한 모델과 소유권](privileges-and-ownership.md#필수-권한-조합)
- [ ] 민감 열을 거버넌스 태그로 분류하고, 정책 조건이 그 태그를 쓰도록 연결했다 — [거버넌스 태그와 ABAC 정책](governed-tags-and-abac.md#abac-정책의-구조)
- [ ] 태그 키와 값의 철자를 허용 값 목록과 대조하고, 정책 적용 결과를 테스트 계정으로 확인했다 — [거버넌스 태그와 ABAC 정책](governed-tags-and-abac.md#5-주의사항)
- [ ] 외부 위치의 루트에 외부 볼륨이나 테이블을 만들지 않고 하위 디렉터리를 썼다 — [베스트 프랙티스와 한도](best-practices-and-limits.md#관리형과-외부-스토리지)
- [ ] 외부 클라우드 경로를 직접 읽는 주체는 UC 밖에서 따로 통제하도록 설계했다 — [볼륨과 외부 스토리지](volumes-and-storage.md#관리형-볼륨과-외부-볼륨)
- [ ] 계보 기록 범위와 이름 변경에 따른 계보 단절을 설계 전에 확인했다 — [계보와 데이터 분류](lineage-and-classification.md#계보의-한계)
- [ ] 분류 자동 태깅을 켜기 전에 Review 패널에서 오탐을 정리했다 — [계보와 데이터 분류](lineage-and-classification.md#5-주의사항)
- [ ] 공유를 회수하기 전에 리시피언트의 소비자를 확인했다 — [데이터 공유와 Clean Rooms](sharing-and-clean-rooms.md#리시피언트에게-공유-열기)
