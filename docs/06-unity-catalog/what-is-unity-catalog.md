# Unity Catalog 개요

> 기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 100

## 한눈에 보기

**Unity Catalog**(UC)는 공식 문서가 "데이터와 AI를 위한 통합 거버넌스 계층(unified governance layer for data and AI)"으로 설명하는 기능입니다. 워크스페이스에서 이루어지는 모든 데이터·AI 작업 아래에서 동작하며, 테이블, 뷰, 볼륨, 함수, 모델 같은 자산에 대한 접근을 한곳에서 제어합니다.

UC의 핵심 요소는 세 가지입니다.

| 요소 | 역할 | 비고 |
|---|---|---|
| 3단계 이름 공간 | `카탈로그.스키마.객체` 형태로 모든 자산을 식별 | 예: `main.sales.orders` |
| 신원(Identity) | 사용자, 서비스 프린시펄, 그룹에 권한을 부여 | 권한 모델은 「권한 모델과 소유권」 페이지에서 다룸 |
| 거버넌스 계층 | 권한, 태그, 정책, 계보, 공유를 한곳에서 관리 | 이 장 전체 |

UC가 자동으로 활성화되는 시점도 문서에 명시되어 있습니다. 공식 문서는 2023년 11월 8일 이후에 만든 모든 Databricks 워크스페이스에서 Unity Catalog가 자동으로 활성화되어 있다고 설명합니다. 그 이전 워크스페이스는 업그레이드 절차를 거쳐야 할 수 있습니다. 업그레이드 세부 절차는 이 장의 범위가 아니므로 공식 문서의 "Upgrade to Unity Catalog" 페이지를 참고하십시오.

## 1. 왜 필요한가

### 이전 방식의 한계

UC 이전에는 워크스페이스마다 Hive 메타스토어가 따로 있었습니다. 이 구조에서는 다음 문제가 자주 나타났습니다.

- 같은 테이블을 여러 워크스페이스에서 쓰려면 워크스페이스마다 메타데이터와 권한을 따로 관리해야 했습니다.
- 권한이 워크스페이스 단위로 흩어져 있어, 한 사람이 어떤 데이터에 접근할 수 있는지 전체 목록을 만들기 어려웠습니다.
- 클러스터나 노트북의 실행 방식에 따라 권한이 다르게 동작하는 경우가 있었습니다.
- 파일 경로 기반 접근은 스토리지 자격 증명을 노트북 곳곳에 흩뿌려 놓는 결과로 이어지기 쉬웠습니다.
- 데이터 계보(어디서 와서 어디로 가는지)와 민감 데이터 식별을 플랫폼 차원에서 제공하지 않았습니다.

UC는 이 문제를 **하나의 메타스토어와 하나의 권한 모델** 로 해결합니다. 같은 메타스토어에 연결된 워크스페이스들은 같은 자산 목록과 같은 권한을 공유합니다. 권한은 자산에 직접 붙고, 노트북이나 클러스터 설정에 의존하지 않습니다.

### 이 장이 해결하는 질문

| 질문 | 답을 얻는 페이지 |
|---|---|
| 누가 어떤 객체를 읽고 쓰고 실행할 수 있는가 | [권한 모델과 소유권](privileges-and-ownership.md) |
| 개별 객체마다 GRANT를 일일이 하지 않고 태그로 정책을 걸 수 있는가 | [거버넌스 태그와 ABAC 정책](governed-tags-and-abac.md) |
| 같은 테이블에서 사용자마다 다른 행과 열을 보여 줄 수 있는가 | [행 필터와 열 마스크](row-filters-and-column-masks.md) |
| 파일과 외부 스토리지 경로를 어떻게 통제하는가 | [볼륨과 외부 스토리지](volumes-and-storage.md) |
| 데이터가 어디서 왔고 민감 데이터가 어디 있는가 | [계보와 데이터 분류](lineage-and-classification.md) |
| 다른 조직이나 외부 사용자와 데이터를 나누려면 | [데이터 공유와 Clean Rooms](sharing-and-clean-rooms.md) |

## 2. 어떻게 동작하는가

### 3단계 이름 공간

UC에서 모든 자산은 세 단계로 식별합니다.

```
catalog.schema.object
```

| 단계 | 설명 | 예 |
|---|---|---|
| 카탈로그(Catalog) | 최상위 데이터 묶음. 공식 문서는 사업부나 개발 수명주기 범위로 나누는 경우가 많다고 설명합니다. | `main`, `prod` |
| 스키마(Schema) | 용도, 프로젝트, 팀 단위로 묶는 두 번째 단계. 문서에서 Database와 같은 의미라고 설명합니다. | `sales`, `ml_team` |
| 객체(Object) | 테이블, 뷰, 볼륨, 함수, 모델 등 실제 자산 | `orders`, `iris_model` |

이름 체계가 세 단계이므로 권한도 같은 계층을 따라 부여합니다. 카탈로그에 권한을 주면 그 아래 스키마와 객체가 대상이 될 수 있는데, 상속 규칙은 [권한 모델과 소유권](privileges-and-ownership.md)에서 자세히 다룹니다.

### 메타스토어

**메타스토어**(Metastore)는 UC의 최상위 컨테이너입니다. 공식 문서는 메타스토어를 "단일 클라우드 리전 안의 모든 Unity Catalog 객체를 담는 최상위 컨테이너"로 설명합니다. 즉 메타스토어는 리전 단위로 존재하며, 여러 리전의 데이터를 하나의 메타스토어에 섞지 않는 것이 기본 구조입니다.

메타스토어 바로 아래에는 카탈로그와 함께 스토리지 자격 증명, 외부 위치, 연결(Connection), 공유(Share), 프로바이더, 리시피언트, Clean Room이 놓입니다. 이 객체들은 카탈로그나 스키마 안이 아니라 메타스토어 직속입니다.

### Securable 객체 종류

**Securable 객체** 는 권한을 부여할 수 있는 UC 객체를 가리키는 공식 용어입니다. 공식 문서가 나열한 종류는 다음과 같습니다.

| 객체 | 설명 | 세부 유형 |
|---|---|---|
| 카탈로그(Catalog) | 최상위 데이터 묶음 | — |
| 스키마(Schema) | 두 번째 묶음 | — |
| 테이블(Table) | 행과 열로 된 구조화 데이터 | 관리형(managed), 외부(external), 외부 카탈로그의 foreign 테이블 |
| 뷰(View) | 저장된 SQL 쿼리로 정의된 읽기 전용 객체 | 구체화된 뷰(materialized view), 메트릭 뷰(metric view) |
| 볼륨(Volume) | 클라우드 스토리지의 비정형 파일 | 관리형, 외부 |
| 함수(Function) | UDF, 저장 프로시저, 등록된 모델 등 재사용 가능한 실행 로직 | — |
| 모델(Model) | UC에 등록된 AI 모델. 문서에서 함수의 한 종류로 구현된다고 설명합니다. | 버전 관리형 또는 비버전 |
| 서비스(Service) | 호출 가능한 AI 자산 | 모델 서비스, 모델 프로바이더 서비스, MCP 서비스, 에이전트 서비스 |
| 시크릿(Secret) | 자격 증명이나 API 토큰 같은 민감한 값. 노출 없이 참조합니다. | — |
| 피처(Feature) | 머신러닝 피처의 정의와 원천 데이터·계산 로직 | — |
| 스토리지 자격 증명(Storage credential) | 특정 클라우드 스토리지 경로에 접근하는 인증 정보 | 메타스토어 직속 |
| 외부 위치(External location) | 클라우드 스토리지 경로와 스토리지 자격 증명의 짝 | 메타스토어 직속 |
| 외부 메타데이터(External metadata) | UC 밖 시스템의 사용자 정의 계보를 표현하는 객체 | 메타스토어 직속 |
| 서비스 자격 증명(Service credential) | 외부 클라우드 서비스 접근용 인증 정보 | 메타스토어 직속 |
| 연결(Connection) | 외부 시스템의 엔드포인트와 자격 증명. 연합, 수집, JDBC, HTTP 접근에 쓰입니다. | 메타스토어 직속 |
| 공유(Share) | 수신자에게 제공할 테이블, 뷰, 볼륨의 논리적 묶음 | 메타스토어 직속 |
| 프로바이더(Provider) | 데이터를 공유하는 외부 조직 | 메타스토어 직속 |
| 리시피언트(Recipient) | 데이터를 받는 외부 조직 또는 사용자 그룹 | 메타스토어 직속 |
| Clean Room | 참여자가 원본 데이터를 노출하지 않고 협업하는 보안 환경 | 메타스토어 직속 |

> **참고** 공식 문서는 서비스 네 종류(모델 서비스, 모델 프로바이더 서비스, MCP 서비스, 에이전트 서비스)를 "Beta"라고 표기한 페이지가 있는 반면, 다른 페이지에서는 일부 서비스 유형을 GA로 표기합니다. 상태 라벨은 페이지마다 다를 수 있으므로 실제 사용 전 해당 기능 페이지의 최신 표기를 확인하십시오.

### 계층 구조

다음 표는 객체가 어디에 속하는지를 보여 줍니다. 표 한 행이 한 단계의 상위 컨테이너입니다.

| 상위 | 하위(직속) |
|---|---|
| 메타스토어 | 카탈로그, 스토리지 자격 증명, 외부 위치, 서비스 자격 증명, 연결, 외부 메타데이터, 공유, 프로바이더, 리시피언트, Clean Room |
| 카탈로그 | 스키마 |
| 스키마 | 테이블, 뷰, 볼륨, 함수, 모델, 서비스, 시크릿, 피처 |

메타스토어 직속 객체는 카탈로그 아래에 있지 않으므로, 카탈로그 권한으로는 이 객체들을 다룰 수 없습니다. 예를 들어 외부 위치는 메타스토어 수준의 권한이나 외부 위치 자체에 부여한 권한으로 관리합니다.

## 3. 어떻게 쓰는가

### 3단계 이름으로 자산 만들기

카탈로그와 스키마를 먼저 만든 뒤 그 안에 객체를 둡니다. 다음 예는 공식 문서의 권한 예제에 나온 이름 체계를 기준으로 한 형태입니다.

```sql
-- 카탈로그와 스키마 목록 확인
SHOW CATALOGS;
SHOW SCHEMAS IN main;

-- 스키마 안의 객체 확인
SHOW TABLES IN main.default;

-- 자산 세부 정보 확인
DESCRIBE TABLE EXTENDED main.default.my_table;
```

`DESCRIBE <securable-type> EXTENDED <catalog>.<schema>.<securable-name>` 형태는 공식 문서의 권한 관리 페이지에 있는 문법입니다. 위 예는 테이블에 대해 그 형태를 쓴 것입니다.

### 현재 사용 가능한 카탈로그 확인

```sql
-- 현재 세션의 카탈로그와 스키마 확인
SELECT current_catalog(), current_schema();

-- 기본 카탈로그와 스키마 지정
USE CATALOG main;
USE SCHEMA default;
```

> **참고** 위 예제의 `main`과 `default`는 공식 문서의 예시 이름입니다. 워크스페이스에 따라 기본 카탈로그 이름이 다를 수 있으니 `SHOW CATALOGS`로 먼저 확인하십시오.

## 4. 트레이드오프

### UC를 쓰는 이득과 비용

| 항목 | 이득 | 비용·제약 |
|---|---|---|
| 중앙 권한 모델 | 자산마다 권한이 붙어 어디서 실행하든 동일하게 동작합니다. | 권한 설계를 먼저 해야 하며, 기존 Hive 메타스토어 구조를 옮길 때 재작업이 필요할 수 있습니다. |
| 3단계 이름 체계 | 카탈로그로 팀이나 환경을 나눌 수 있습니다. | 이름이 길어지고, 기존 2단계 이름을 쓰는 코드는 수정이 필요합니다. |
| 메타스토어 단위 리전 구조 | 리전별 데이터 주권과 격리를 맞추기 쉽습니다. | 리전을 넘는 공유와 거버넌스는 별도 설계가 필요합니다. 이 장의 공유 페이지에서 다룹니다. |
| 통합 거버넌스 기능 | 태그, 정책, 계보, 분류, 공유를 한 계층에서 씁니다. | 기능마다 상태 라벨이 달라, GA와 Beta를 섞어 설계하면 운영 중 기능 제약을 만날 수 있습니다. |

### 언제 쓰지 않는가

- 워크스페이스 하나에서 단발성 실험만 하며 권한 관리가 필요 없는 경우에도 UC를 기본으로 쓰는 것이 일반적입니다. 다만 UC 없이 파일 경로만으로 작업하는 방식이 허용되는지는 워크스페이스 설정과 컴퓨트 구성에 따라 다르므로, 실제 환경에서 확인하십시오.
- UC가 관리하지 않는 외부 시스템이 파일을 직접 읽고 쓰는 구조라면, UC 권한만으로는 접근을 막을 수 없습니다. 이 경우 외부 볼륨과 클라우드 측 접근 제어를 함께 설계해야 합니다. 자세한 내용은 [볼륨과 외부 스토리지](volumes-and-storage.md)에서 다룹니다.

## 5. 주의사항

> **주의** 메타스토어 직속 객체(외부 위치, 스토리지 자격 증명, 공유, 리시피언트 등)는 카탈로그 권한으로 관리되지 않습니다. 권한 설계 시 이 객체들의 권한을 따로 검토하십시오.

> **주의** UC 객체 이름은 최대 255자입니다. 공식 문서는 "Object names cannot exceed 255 characters"라고 명시합니다.

> **참고** 이름에 하이픈이나 공백 같은 특수 문자가 있으면 백틱(`` ` ``)으로 감싸야 합니다. 공식 문서 예시는 `` `finance-team` `` 형태를 씁니다.

- 카탈로그를 환경(예: `dev`, `prod`)으로 나눌지, 사업부로 나눌지는 초기에 정해야 합니다. 나중에 바꾸면 이름과 권한을 모두 옮겨야 합니다.
- 기본으로 생성되는 `default` 스키마나 워크스페이스 카탈로그를 운영 데이터 용도로 쓰지 않는 것을 권장합니다.
- 계정 수준(account) 관리자와 메타스토어 관리자(metastore admin)는 권한 범위가 다릅니다. 두 역할을 구분해 설계하십시오. 역할 세부는 공식 문서의 Admin roles 페이지를 참고합니다.
