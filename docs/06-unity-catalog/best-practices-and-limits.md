# 베스트 프랙티스와 한도

> 기준일: 2026-10-28 · 근거: 공식 문서

## 한눈에 보기

이 페이지는 앞의 여덟 페이지에서 다룬 기능을 실제 설계에 옮길 때의 **기준** 을 모읍니다. 공식 베스트 프랙티스 페이지의 권고, 자원 한도 페이지의 수치, 릴리즈 노트의 상태 변화를 한곳에 정리했습니다. 권고는 공식 문서 표현을 따르고, 이 장의 해석은 "이 장의 판단"으로 구분해 표시합니다.

## 1. 설계 원칙

### 카탈로그와 스키마

| 권고 | 근거 |
|---|---|
| 카탈로그와 스키마는 환경, 팀, 사업부 또는 그 조합 기준으로 나눕니다. | 공식 베스트 프랙티스 |
| 환경과 데이터의 격리 요구가 다르면 카탈로그를 특정 워크스페이스에 바인딩합니다. | 공식 베스트 프랙티스 |
| 운영 카탈로그와 스키마의 소유자는 개인이 아니라 그룹으로 둡니다. | 공식 베스트 프랙티스 |
| 팀마다 스키마를 하나씩 두고, 팀에 `USE CATALOG`, `USE SCHEMA`, `CREATE TABLE`을 줍니다. | 공식 베스트 프랙티스 |
| 메타스토어는 리전당 하나입니다. 공식 문서: "You can have only one metastore per region." | 공식 베스트 프랙티스 |
| 자주 쓰는 외부 테이블을 둘 이상의 메타스토어에 등록하지 않습니다. | 공식 베스트 프랙티스 |

### 그룹과 권한

| 권고 | 근거 |
|---|---|
| 주체는 계정 수준에서 프로비저닝합니다. IdP가 지원하지 않으면 SCIM을 씁니다. | 공식 베스트 프랙티스 |
| 그룹은 IdP에서 정의하고 관리합니다. 워크스페이스에서 사용자나 그룹을 수동으로 바꾸지 않습니다. | 공식 베스트 프랙티스 |
| 사용자에게 직접 주기보다 그룹을 통해 권한을 줍니다. 대부분의 소유권도 그룹에 둡니다. | 공식 베스트 프랙티스 |
| 메타스토어 관리자는 꼭 필요할 때만 지정합니다. | 공식 베스트 프랙티스 |
| `ALL PRIVILEGES`와 `MANAGE`는 아껴 씁니다. | 공식 베스트 프랙티스 |
| 발견과 접근 요청을 돕기 위해 카탈로그에 `BROWSE`를 "All account users" 그룹에 줄 수 있습니다. | 공식 베스트 프랙티스 |
| 뷰와 메트릭 뷰의 소유권을 그룹으로 넘기면 협업 편집이 가능합니다. | 공식 베스트 프랙티스 |
| `USE CATALOG`와 `USE SCHEMA`만으로는 `SELECT`나 `READ`가 생기지 않습니다. 선행 조건입니다. | 공식 베스트 프랙티스 |

> **참고** 공식 문서는 "All account users" 그룹을 `BROWSE` 대상으로 쓰라고 권고하지만, 이 그룹에 `SELECT`를 주라는 뜻은 아닙니다. 발견 가능성과 데이터 접근 권한은 분리해서 설계하십시오.

### 서비스 프린시펄

| 권고 | 근거 |
|---|---|
| 잡은 서비스 프린시펄로 실행합니다. 사용자가 운영 데이터를 실수로 덮어쓰지 않게 합니다. | 공식 베스트 프랙티스 |
| 운영 테이블에 대한 직접 `MODIFY` 접근은 서비스 프린시펄에게만 줍니다. | 공식 베스트 프랙티스 |

### 관리형과 외부 스토리지

| 권고 | 근거 |
|---|---|
| 대부분의 경우와 새 테이블에는 관리형 테이블을 씁니다. | 공식 베스트 프랙티스 |
| 외부 테이블은 Hive 메타스토어 업그레이드, 특정 재해 복구 요구, Delta·Iceberg가 아닌 형식, 외부 접근이 필요할 때 씁니다. | 공식 베스트 프랙티스 |
| 외부 테이블은 스키마당 외부 위치 하나로 만듭니다. | 공식 베스트 프랙티스 |
| 대부분의 파일에는 관리형 볼륨을 쓰고, 랜딩 영역과 스테이징에는 외부 볼륨을 씁니다. | 공식 베스트 프랙티스 |
| `CREATE EXTERNAL LOCATION`은 신뢰할 수 있는 관리자나 데이터 엔지니어에게만 줍니다. | 공식 베스트 프랙티스 |
| 최종 사용자에게 외부 위치의 일반 `READ FILES`나 `WRITE FILES`를 주지 않고, 볼륨을 씁니다. | 공식 베스트 프랙티스 |
| 외부 위치의 루트에 외부 볼륨이나 테이블을 만들지 않고, 하위 디렉터리를 씁니다. | 공식 베스트 프랙티스 |
| 외부 위치에는 파일 이벤트를 켭니다. | 공식 베스트 프랙티스 |
| DBFS 루트로 쓰였거나 쓰이는 버킷은 재사용하지 않습니다. | 공식 베스트 프랙티스 |

### 공유와 계보

| 권고 | 근거 |
|---|---|
| 클라우드 리전이나 프로바이더를 넘는 공유는 Databricks-to-Databricks OpenSharing을 씁니다. | 공식 베스트 프랙티스 |
| 자주 쓰지 않는 테이블은 OpenSharing으로 제공합니다. 공식 문서는 이그레스 비용이 발생한다고 설명합니다. | 공식 베스트 프랙티스 |
| 자주 공유 접근이 필요한 워크스페이스는 같은 리전에 둡니다. | 공식 베스트 프랙티스 |
| 계보 그래프는 메타스토어 범위이며 리전이나 플랫폼 경계를 넘지 않습니다. | 공식 베스트 프랙티스 |

> **참고** 공식 베스트 프랙티스 페이지는 태그와 ABAC, 명명 규칙에 대한 항목을 싣지 않습니다. 이 영역은 「거버넌스 태그와 ABAC 정책」 페이지와 이 장의 4절에서 다룬 기능 문서와 이 장의 판단을 따르십시오.

## 2. 설계 체크리스트 (이 장의 판단)

아래 표는 공식 권고를 설계 단계의 질문으로 바꾼 것입니다. 공식 문서의 문구가 아니라 이 장의 정리입니다.

| 질문 | 확인할 페이지 |
|---|---|
| 카탈로그와 스키마 경계가 팀 또는 환경과 맞는가 | 「Unity Catalog 개요」 페이지 |
| 권한은 그룹에 붙어 있고, 소유자는 그룹인가 | 「권한 모델과 소유권」 페이지 |
| 진입 권한(`USE CATALOG`, `USE SCHEMA`)을 빠뜨리지 않았는가 | 「권한 모델과 소유권」 페이지 |
| 민감 열은 태그로 분류되고, 정책이 그 태그를 쓰는가 | 「거버넌스 태그와 ABAC 정책」 페이지, 「계보와 데이터 분류」 페이지 |
| 테이블 단위 규칙이 ABAC로 옮길 수 있는 규칙인가 | 「행 필터와 열 마스크」 페이지 |
| 외부 위치는 스키마당 하나인가, 루트에 객체를 만들지 않았는가 | 「볼륨과 외부 스토리지」 페이지 |
| 권한을 회수하기 전에 소비자가 파악되어 있는가 | 「권한 모델과 소유권」 페이지, 아래 4절 |
| 공유의 이그레스 비용과 리전 배치를 검토했는가 | 「데이터 공유와 Clean Rooms」 페이지 |
| 메트릭 정의의 소비처가 파악되어 있는가 | 「메트릭 뷰의 거버넌스」 페이지 |

## 5. 권한 회수 전 점검

권한을 줄이거나 공유를 회수하면 그 권한을 쓰던 소비자가 조용히 실패할 수 있습니다. 공식 문서가 이 주제의 절차를 따로 설명하지는 않으므로, 아래는 이 장의 판단에 따른 절차입니다.

1. 회수 대상 객체와 권한을 `SHOW GRANTS`로 확인합니다.
2. 같은 객체를 참조하는 노트북, 잡, 대시보드, Genie 공간, 외부 코드를 찾습니다. 여러 리포지토리나 워크스페이스를 함께 쓴다면 전체 코드 검색을 합니다.
3. 해당 권한으로 실행되는 주체(사용자, 서비스 프린시펄, 그룹)를 확인합니다.
4. 공유라면 리시피언트의 조회 이력을 감사 로그에서 확인합니다(12장).
5. 소비자가 확인된 뒤 회수 시점과 복구 방법을 함께 정합니다.

> **주의** 회수가 필요한 요청 범위를 넘어 권한을 더 넓게 줄이는 변경은 선택지로만 제시하고, 소비자 확인 없이 실행하지 마십시오.

## 6. 흔한 실수

| 실수 | 결과 | 대응 |
|---|---|---|
| 사용자 개인에게 직접 `GRANT` | 인원 변경 때 권한 정리가 어려움 | 그룹에 주고 사람을 그룹에 넣음 |
| `USE CATALOG`만 주고 `SELECT` 누락 | 조회 실패 | 진입 권한과 객체 권한을 함께 확인 |
| `SELECT`만 주고 `USE SCHEMA` 누락 | 조회 실패 | 「권한 모델과 소유권」 페이지의 필수 권한 조합 참조 |
| 외부 위치 루트에 외부 테이블 생성 | 관리 경계가 흐려짐 | 하위 디렉터리를 씀 |
| 태그 이름 오타 | 정책이 대상을 찾지 못함 | 태그 허용 값 목록을 문서화하고 테스트 |
| 분류 자동 태깅을 검토 없이 켬 | 분류 태그가 정책 조건에 걸려 있으면 접근 제어가 예기치 않게 바뀔 수 있음 | Review 패널에서 오탐 정리 후 켬 |

## 7. 주의사항

> **주의** 이 장은 2026-10-28 기준 공식 문서와 릴리즈 노트를 확인한 결과입니다. 상태 라벨과 한도는 바뀔 수 있으므로, 설계 문서에 옮기기 전에 각 페이지의 참고 문서 링크에서 다시 확인하십시오.

> **주의** 정책, 공유, 권한 변경은 운영 환경에 바로 적용하기 전에 테스트 카탈로그나 개발 워크스페이스에서 먼저 검증하십시오.

- 12장에서 다루는 시스템 테이블과 감사 로그로 권한 변경과 접근 이력을 추적하는 방법을 확인하십시오.
- AI/BI와 Genie가 메트릭 뷰와 데이터를 어떻게 소비하는지는 07장에서 다룹니다.
