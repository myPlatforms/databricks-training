# 계보와 데이터 분류

> 기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 200

## 한눈에 보기

**데이터 계보**(Data lineage)는 데이터가 어디서 와서 어디로 가는지를 기록한 흐름입니다. UC는 쿼리를 실행하면 테이블과 열 단위의 상·하위 관계를 자동으로 기록하고, 카탈로그 탐색기에서 그래프로 보여 줍니다.

**데이터 분류**(Data Classification)는 테이블을 훑어 민감 데이터를 찾고 태그(`class.*`)를 붙이는 기능입니다. 공식 문서는 이 기능이 에이전트형 AI 시스템을 사용하며, 대규모 언어 모델(LLM)을 기반으로 민감 데이터를 찾아 태그를 붙이고, 그 결과가 접근 제어에 쓰일 수 있다고 설명합니다.

두 기능은 거버넌스의 "무엇이 어디에 있고 어디로 흘러가는가"를 답합니다.

| 질문 | 기능 | 기록 위치 |
|---|---|---|
| 이 테이블은 어디서 만들어졌고 누가 쓰는가 | 계보 | 카탈로그 탐색기의 Lineage 탭, 계보 시스템 테이블 |
| 이 테이블에 민감 데이터가 있는가 | 데이터 분류 | 분류 결과 페이지, `system.data_classification.results` |

> **참고** 계보와 분류 결과를 시스템 테이블로 조회하는 방법과 감사 로그는 12장에서 다룹니다. 이 페이지는 기능 동작과 제약을 설명합니다.

## 1. 왜 필요한가

### 이전 방식의 한계

- 테이블 A가 틀렸을 때 영향을 받는 대시보드와 잡을 찾으려면 사람이 노트북과 잡 정의를 하나씩 열어 봐야 했습니다.
- 민감 열이 어느 테이블에 들어 있는지 알 수 없으면, 접근 정책을 걸 대상부터 특정할 수 없습니다.
- 외부 시스템(원천 DB, 외부 ETL 도구)에서 들어온 데이터의 출처를 플랫폼 안에서 보여 줄 수단이 없었습니다.

계보는 쿼리를 실행할 때 자동으로 기록되므로, 사람이 문서를 따로 만들지 않아도 영향 범위를 볼 수 있습니다. 데이터 분류는 민감 열을 **사람이 찾는 대신** 자동으로 찾아 태그를 붙입니다. 그 태그는 「거버넌스 태그와 ABAC 정책」 페이지의 ABAC 정책과 연결되어 접근 제어의 입력이 됩니다.

## 2. 어떻게 동작하는가

### 계보가 기록하는 범위

공식 문서가 설명하는 계보 기록 대상은 다음과 같습니다.

| 대상 | 기록 내용 |
|---|---|
| 테이블, 뷰 | 어떤 쿼리나 파일이 테이블을 채우는지, 어떤 잡, 노트북, 대시보드가 소비하는지 |
| 열 | Databricks에서 실행한 쿼리에 대해 열 단위 계보가 자동으로 기록됩니다. |
| 잡, 대시보드 | 테이블의 Lineage 탭에 소비자로 나타납니다. |
| 노트북 | 계보 그래프에 작업 부하(workload)로 나타납니다. |
| ML 모델과 모델 서비스 | 모델 버전이 그래프의 노드가 되고, 모델 서비스와 외부 모델 제공자는 자체 계보를 가집니다. |
| 외부 자산 | 외부 메타데이터(External metadata)로 등록하면 같은 그래프에 표시됩니다. |
| UDF | SQL, Python, Scala UDF에 대해 테이블 수준 계보를 기록합니다. |
| 임시 테이블 | 임시 테이블은 노드로 나타나지 않고, 영구 상류·하류 테이블이 직접 연결됩니다. 영구 스테이징 테이블은 별도 노드로 나타납니다. |

### 계보 확인 요구 사항

| 항목 | 내용 |
|---|---|
| 테이블 등록 | 테이블이 Unity Catalog 메타스토어에 등록되어 있어야 합니다. |
| 쿼리 방식 | Spark DataFrame 또는 노트북, SQL 쿼리 편집기 같은 Databricks SQL 인터페이스를 써야 합니다. |
| 조회 권한 | 계보를 보려면 상위 카탈로그에 최소한 `BROWSE` 권한이 있어야 하며, 카탈로그는 워크스페이스에서 접근 가능해야 합니다. |
| 노트북·잡·대시보드 | 각각의 워크스페이스 권한이 필요합니다. 공식 문서는 Unity Catalog를 사용하는 파이프라인에 CAN VIEW 권한이 필요하다고 설명합니다. |
| 런타임 | Delta 테이블 사이의 스트리밍 계보는 Databricks Runtime 11.3 LTS 이상, Lakeflow 파이프라인 열 계보는 13.3 LTS 이상입니다. |
| 방화벽 | 일부 배포에서는 워크스페이스 리전의 Amazon Kinesis 엔드포인트에 대한 아웃바운드 규칙이 필요할 수 있습니다. |

### 계보 보존과 조회

| 항목 | 내용 |
|---|---|
| 카탈로그 탐색기의 계보 | 무기한 보관됩니다. 기본 조회 기간은 1년입니다. |
| 계보 시스템 테이블 | 1년 롤링 기간을 유지합니다. |
| 2024년 9월 1일 이전 계보 | 사용할 수 없습니다. 공식 문서: "Lineage data captured before September 1, 2024 is not available." |

조회 방법은 다음과 같습니다.

- 카탈로그 탐색기에서 테이블을 열고 **Lineage** 탭을 엽니다.
- `See Lineage Graph`를 선택하면 대화형 그래프가 열립니다.
- 간선(edge)을 선택하면 **Lineage details** 패널이 열리고, 열을 클릭하면 관련 상·하류 열이 보입니다.
- 잡과 대시보드는 Lineage 탭에서 `Jobs`나 `Dashboards` 필터로 봅니다.
- UDF는 함수를 카탈로그 탐색기에서 열고 Lineage 탭에서 봅니다.

### 데이터 분류 동작

| 항목 | 내용 |
|---|---|
| 대상 | 테이블, 스트리밍 테이블, 구체화된 뷰. 일반 뷰는 Beta입니다. |
| 증분 스캔 | 새 테이블과 열은 생성 후 보통 24시간 안에 스캔된다고 공식 문서가 설명합니다. |
| 분류 체계 | 글로벌 태그, 지역 태그, PII, PCI DSS, GDPR, HIPAA 같은 규정 준수 프레임워크로 나뉩니다. 세부 목록은 별도 페이지에 있습니다. |
| 제외 대상 | 메트릭 뷰는 스캔하지 않습니다. 안전하지 않은 뷰 정의는 건너뛰고 `UNSUPPORTED_VIEW_DEFINITION` 상태로 보고합니다. |
| 결과 저장 | 결과 페이지와 `system.data_classification.results` 시스템 테이블에 기록됩니다. 샘플 값은 이 테이블에 `SELECT` 권한이 있는 사용자만 봅니다. |
| 자동 태그 | 자동 태깅이 켜지면 탐지 결과를 `class.*` 태그로 기존 및 새 탐지 대상에 붙입니다. |

## 3. 어떻게 쓰는가

### 계보 조회 (시스템 테이블 없이)

계보는 카탈로그 탐색기에서 보는 것이 기본 경로입니다. 프로그램으로 조회하려면 계보 시스템 테이블을 씁니다. 세부 테이블 구조와 쿼리 예제는 12장에서 다룹니다.

Genie Code는 `/getTableLineages` 명령으로 계보 질문에 답할 수 있다고 공식 문서가 설명합니다. Genie Code의 사용법은 [11장 Genie Code](../11-developer-tools/genie-code/README.md)를 참고하십시오.

### 분류 결과 확인과 자동 태그 설정

데이터 분류는 카탈로그 탐색기의 분류 결과 페이지에서 켜고 확인합니다. 공식 문서의 권한 요구 사항은 다음과 같습니다.

| 작업 | 필요한 권한 |
|---|---|
| 분류 켜기 | 카탈로그 소유 또는 카탈로그에 대한 `MANAGE` |
| 자동 태깅 켜기 (카탈로그 수준) | `USE CATALOG`, 태그에 대한 `APPLY TAG`, 태그에 대한 `ASSIGN` |
| 자동 태깅 켜기 (메타스토어 수준) | 메타스토어 관리자이면서 태그에 대한 `ASSIGN` |
| 결과 보기 | `MANAGE`, `READ METADATA`, 또는 `USE CATALOG`·`USE SCHEMA`·`SELECT`, 그리고 서버리스 컴퓨트 |

> **참고** 공식 문서는 결과 페이지의 자동 태깅 상태를 **Active**, **Inactive** 로 표기합니다. 메타스토어 수준에서는 일부 카탈로그에만 켜진 상태를 **Partially Active** 로 표시합니다.

결과 페이지의 **Review** 패널에서는 두 탭을 씁니다.

- **Detected Columns**: 오탐(false positive)을 제외 처리합니다.
- **User Access**: 분류별 접근자와 해당 분류에 걸린 ABAC 정책을 봅니다. 이 탭에서 분류 태그가 미리 채워진 마스킹 정책을 만들 수 있다고 공식 문서가 설명합니다.

### 분류 태그를 정책 조건으로 쓰기

분류 결과는 `class.*` 태그로 붙으므로, 「거버넌스 태그와 ABAC 정책」 페이지의 정책 조건에 그대로 쓸 수 있습니다. 공식 문서는 다음과 같은 조건 형태를 예로 듭니다.

```sql
-- 이메일 분류 태그가 붙은 열을 대상으로 한 조건 (정책 WHEN 또는 MATCH COLUMNS 절에서 사용)
has_tag("class.email_address")
```

조건의 자세한 사용법과 정책 생성 문법은 [거버넌스 태그와 ABAC 정책](governed-tags-and-abac.md)과 [행 필터와 열 마스크](row-filters-and-column-masks.md)을 참고하십시오.

## 4. 트레이드오프

### 계보의 한계

공식 문서는 다음 경우 계보가 제대로 잡히지 않거나 빠진다고 명시합니다. 그대로 옮깁니다.

| 한계 | 공식 문서 원문 또는 요지 |
|---|---|
| 잡 실행 링크 누락 | `runs submit` 또는 `spark submit` 작업 유형으로 실행한 잡은 잡 실행 링크가 기록되지 않습니다. 테이블과 열 계보는 기록됩니다. |
| 이름 변경 | 카탈로그, 스키마, 테이블, 뷰, 열의 이름을 바꾸면 계보가 이어지지 않습니다. |
| 체크포인트 | Spark SQL 데이터셋 체크포인팅은 계보 기록을 막습니다. |
| 임시 뷰 | "Global temp views are not captured in lineage." |
| RDD | RDD는 기록되지 않습니다. |
| 롤백 | 트랜잭션이 롤백되어도 계보 이벤트는 남습니다. |
| 정보 스키마 | "Tables under system.information_schema are not captured in lineage." |
| 경로 참조 | 소스나 타깃을 테이블 이름이 아니라 경로로 참조하면 열 계보가 표시되지 않습니다. 시스템 테이블에는 경로 기반 계보가 기록됩니다. |
| UDF 열 계보 | "Column-level UDF lineage is not captured." UDF 기반 변환은 열 사이 관계를 가릴 수 있습니다. |
| SQL UDF | `INSERT`, `UPDATE`, `MERGE` 문에서 호출된 SQL UDF는 기록되지 않습니다. |
| 테이블 값 함수, ML 함수 | 테이블 값 함수, ML 함수, 피처 명세 함수는 계보에 기록되지 않습니다. UDF 계보는 시스템 테이블로 조회할 수 없습니다. |
| 워크스페이스 간 | 같은 메타스토어를 공유하는 다른 워크스페이스에서 계보는 보이지만, 워크스페이스 수준 객체 세부 정보는 소속 워크스페이스 밖에서 가려집니다. |

### 분류 자동화의 한계

- 분류는 **AI 기반 탐지** 이므로 오탐과 누락이 있을 수 있습니다. 공식 문서도 오탐을 검토 패널에서 제외하라고 안내합니다.
- 메트릭 뷰는 스캔하지 않습니다. 메트릭 정의에 민감 열이 있다면 원본 테이블 쪽 분류 결과를 봐야 합니다.
- 일반 뷰 스캔은 Beta입니다. 뷰를 분류 대상으로 삼기 전에 해당 워크스페이스에서 상태를 확인하십시오.
- 2026년 10월 15일 릴리즈 노트는 분류에 50개 클래스와 16개 국가·지역 지원을 추가했다고 공지했습니다. 상태 라벨은 릴리즈 노트에 없습니다.

### 언제 쓰지 않는가

- 계보를 외부 도구에서 기록해야 하는 경우, 외부 메타데이터로 등록하는 방식이 필요합니다. 플랫폼 밖 파이프라인의 세부 계보는 자동으로 잡히지 않습니다.

## 5. 주의사항

> **주의** 계보의 2024년 9월 1일 이전 데이터는 조회할 수 없습니다. 오래된 워크로드의 영향 범위를 계보로 확인하려면 기록 시작 시점을 먼저 확인하십시오.

> **주의** 이름을 바꾸면 계보가 끊깁니다. 객체 이름 변경은 계보 기록을 잃는다는 점을 감안해 계획하십시오.

> **주의** 분류 자동 태깅을 켜면 기존과 앞으로 생길 탐지 결과에 `class.*` 태그가 붙습니다. 태그 정책이나 정책 조건이 이 태그에 걸려 있으면, 자동 태그 한 번으로 접근 제어 결과가 바뀔 수 있습니다. 먼저 **Review** 패널에서 오탐을 정리하십시오.

- 분류 결과를 보는 사용자는 샘플 값까지 볼 수 있는지 `system.data_classification.results`의 `SELECT` 권한으로 따로 통제하십시오.
- 분류 결과를 바로 마스킹 정책으로 연결하기보다, 먼저 소규모 카탈로그에서 오탐 비율을 확인하는 것을 권장합니다.
- 외부 자산을 계보 그래프에 표시하려면 외부 메타데이터로 미리 등록해야 합니다. 등록 방식은 공식 문서의 외부 메타데이터 설명을 확인하십시오.
