    퀴즈와 체크리스트¶

    기준일: 2026-10-29 · 근거: 이 장 본문 · 수준: 100~300

    이 장에서 다룬 내용을 확인하는 문제입니다. 정답을 펼치면 해설과 근거 페이지로 가는 링크가 있습니다.

    퀴즈¶

    1. 계정 관리자와 워크스페이스 관리자의 역할 차이로 옳은 것은? (수준 100)¶

    • A. 워크스페이스 관리자는 계정 수준의 사용자와 서비스 프린시펄을 수정하거나 삭제할 수 있다
    • B. 계정 관리자는 계정 수준 ID와 워크스페이스 접근을 관리하고, 워크스페이스 관리자는 계정 수준 ID를 수정하거나 삭제할 수 없다
    • C. 계정 관리자는 계정 전체의 토큰을 조회하거나 폐기할 수 없고, 워크스페이스 관리자만 가능하다
    • D. 계정 콘솔의 보안 설정은 워크스페이스 관리자만 바꿀 수 있다
    정답과 해설

    정답: B — 본문은 계정 관리자가 계정 수준 사용자·서비스 프린시펄·그룹을 추가·수정·삭제하고 워크스페이스 접근을 부여한다고 설명합니다. 워크스페이스 관리자는 계정 수준 ID를 수정하거나 삭제할 수 없으므로, 퇴사자 처리 절차를 계정 관리자와 나눠 정의해야 합니다. A는 이 제약과 반대이고, C는 계정 관리자가 계정 전체 토큰을 모니터링하고 폐기할 수 있다는 본문과 다릅니다. D도 계정 관리자가 계정 콘솔 보안 설정을 맡는다는 본문과 다릅니다.

    근거: 보안 모델 개요 — 2.2 계정과 워크스페이스의 역할

    2. 계정 수준 보안 기능이 기본으로 제공되도록 바뀌었다는 설명의 올바른 이해는? (수준 100)¶

    • A. 기본 제공되면 계정의 보안 설정이 자동으로 강화된다
    • B. 기능을 쓸 수 있는 상태가 되었을 뿐이며, 관리자가 설정해야 효과가 나고 기존 구성도 자동으로 바뀌지 않는다
    • C. 기본 제공된 기능은 여전히 Previews 페이지에서 먼저 켜야 한다
    • D. 기본 제공 여부는 워크스페이스 로그에서만 확인할 수 있다
    정답과 해설

    정답: B — 릴리즈 노트는 계정 수준 보안 기능이 GA 시점에 모든 계정에 바로 제공되며, Previews 페이지에서 따로 켤 필요가 없다고 설명합니다. 동시에 관리자는 여전히 기능을 설정해야 효과가 있고, 기본 제공이 계정의 보안 구성을 자동으로 바꾸거나 새 통제를 강제하지 않는다고 명시합니다. A와 C는 이 설명과 반대이고, D는 본문에 없는 내용입니다.

    근거: 보안 모델 개요 — 2.3 계정 수준 보안 기능의 기본 제공 변경

    3. 인증 방식으로 문서가 권장하는 쪽은? (수준 100)¶

    • A. PAT를 기본으로 권장하고 OAuth는 예외적인 경우에만 쓴다
    • B. OAuth를 중심으로 하고, PAT는 지원되지만 OAuth 사용을 권장한다
    • C. PAT는 더 이상 지원되지 않으므로 OAuth만 쓸 수 있다
    • D. OAuth는 사람만 쓸 수 있고, 잡은 반드시 PAT로 실행해야 한다
    정답과 해설

    정답: B — 인증 페이지는 OAuth U2M(사람)과 OAuth M2M(서비스 프린시펄)을 기본 축으로 두고, 개인 액세스 토큰(PAT)은 지원되지만 OAuth 사용을 권장한다고 설명합니다. 무인 작업은 서비스 프린시펄의 OAuth M2M으로 인증하는 것이 본문의 구조입니다. A, C, D는 모두 본문과 다릅니다.

    근거: 인증과 토큰 — 인증 방식 비교

    4. IdP에서 퇴사자 계정을 삭제했습니다. 자동 ID 관리를 쓰는 환경에서 함께 점검할 것은? (수준 200)¶

    • A. 삭제 즉시 모든 토큰이 무효화되므로 추가 작업이 없다
    • B. 해당 사용자의 개인 액세스 토큰을 따로 폐기한다
    • C. 워크스페이스 관리자가 계정 콘솔에서 해당 사용자를 삭제한다
    • D. 그룹 멤버십은 IdP 변경과 무관하게 Databricks에서 계속 유지된다
    정답과 해설

    정답: B — IdP에서 삭제된 사용자는 "Active: Removed From [IdP]" 상태가 되고, 다음 동기화에서 Databricks가 비활성화합니다. 본문은 이 사용자의 개인 액세스 토큰도 폐기하라고 권장합니다. A는 즉시 무효화가 아니라는 점에서 틀립니다. C는 워크스페이스 관리자가 계정 수준 사용자를 수정·삭제할 수 없다는 본문과 반대입니다. D는 그룹 멤버십이 활동 시점에 IdP에서 새로 가져온다는 본문과 다릅니다.

    근거: ID와 접근 — 자동 ID 관리 (AIM)

    5. 야간 잡을 서비스 프린시펄로 운영합니다. 담당자가 퇴사해도 잡이 깨지지 않게 하려면? (수준 200)¶

    • A. 잡을 만든 담당자의 개인 계정으로 실행해 권한을 한 곳에서 관리한다
    • B. 서비스 프린시펄로 잡을 실행하고, 실행하는 사용자에게 Service Principal User 역할을 명시적으로 부여한다
    • C. 서비스 프린시펄을 관리하는 사람은 자동으로 실행 권한을 받으므로 따로 줄 필요가 없다
    • D. 여러 사용자가 같은 개인 토큰을 공유해 잡을 실행한다
    정답과 해설

    정답: B — 본문은 잡과 CI/CD를 서비스 프린시펄로 실행하는 것을 원칙으로 하고, 실행자에게 Service Principal User 역할을 명시적으로 부여하라고 설명합니다. 사용자 권한은 서비스 프린시펄 대상의 실행 권한으로 주면 사용자가 떠나도 잡이 실패하지 않습니다. C는 관리자 역할이 Service Principal User 역할을 상속하지 않는다는 본문과 반대입니다. A와 D는 사람 계정이나 공유 토큰에 기대는 방식으로, 본문이 피하라고 한 구성입니다.

    근거: ID와 접근 — 3.1 서비스 프린시펄 만들고 배정하기

    6. 감사 로그 시스템 테이블을 조회할 때 본문이 권장하는 필터는? (수준 200)¶

    • A. event_time으로만 필터링하는 것이 가장 빠르다
    • B. event_date로 필터링하면 조회가 빨라지며, event_time만 쓰면 조회가 느려질 수 있다
    • C. 문서는 날짜 필터 없이 전체 기간을 조회하라고 권장한다
    • D. 감사 로그에는 event_date 컬럼이 없으므로 event_time을 써야 한다
    정답과 해설

    정답: B — 감사 로그 페이지는 성능을 위해 event_time보다 event_date로 필터링하라고 권장하며, event_time만 쓰면 조회가 느려질 수 있다고 설명합니다. A는 본문과 반대이고, C는 날짜 필터를 권장하는 본문과 다릅니다. D는 event_date가 감사 로그의 컬럼으로 본문에 나온다는 점에서 틀립니다.

    근거: 감사 로그와 시스템 테이블 — 감사 로그 시스템 테이블 (system.access.audit)

    7. 팀별 비용 귀속을 위해 서버리스 사용량 정책을 설계합니다. 올바른 설명은? (수준 200)¶

    • A. 클래식 컴퓨트 사용량에도 정책 태그가 붙어 팀별 귀속이 가능하다
    • B. 정책은 할당된 사용자가 만든 서버리스 활동에 태그를 붙이며, 클래식 컴퓨트에는 적용되지 않는다
    • C. 정책을 바꾸면 과거 사용량까지 소급해 새 태그로 다시 집계된다
    • D. 잡이 실행하는 파이프라인은 잡의 정책을 항상 상속하므로 따로 설정할 필요가 없다
    정답과 해설

    정답: B — 서버리스 사용량 정책은 할당된 사용자가 만든 서버리스 활동(노트북, 잡, Lakeflow pipelines 등)에 정책의 사용자 정의 태그를 붙이며, 클래식 컴퓨트 리소스에는 태그를 붙이지 않습니다. A는 클래식 적용 제외라는 본문과 반대입니다. C는 변경이 변경 시점 이후 사용량부터 적용된다는 본문과 다르고, D는 잡이 트리거한 파이프라인이 잡의 정책을 상속하지 않는다는 본문과 반대입니다.

    근거: 비용 관리 — 서버리스 사용량 정책 (Serverless usage policies)

    8. 예산 차단(Block usage)으로 지출 상한을 확실히 막을 수 있는가? (수준 300)¶

    • A. 가장 높은 임계값에서 차단을 켜면 지출 상한이 확실히 보장된다
    • B. 차단은 Unity Gateway 예산에서만 쓸 수 있고 근사치로 동작하며, 절대 상한을 보장하지 않는다
    • C. 워크스페이스 단위 예산이든 계정 전체 예산이든 차단 기능을 똑같이 쓸 수 있다
    • D. 차단을 켜면 진행 중인 요청도 즉시 중단되어 지출이 멈춘다
    정답과 해설

    정답: B — 예산 페이지는 차단이 Unity Gateway 예산에서만 가능하며, 근사치로 동작해 한도에 도달하기 전에 막히거나 차단 적용 전에 지출이 한도를 넘을 수 있다고 설명합니다. 절대적 지출 상한을 보장하지 않는다는 점도 명시합니다. A는 보장이 없다는 본문과 반대이고, C는 차단 적용 범위를 잘못 말한 것입니다. D는 진행 중인 요청이 중단되지 않는다는 본문과 반대입니다.

    근거: 비용 관리 — 예산 (Budgets)

    9. IP 액세스 목록으로 PrivateLink를 통해 들어오는 사설 트래픽을 막을 수 있습니까? (수준 300)¶

    • A. 가능하다. IP 액세스 목록은 사설 연결 트래픽에도 똑같이 적용된다
    • B. 불가능하다. IP 액세스 목록은 인터넷 트래픽에만 적용되므로 PrivateLink로 들어오는 사설 IP는 막지 못한다
    • C. 가능하다. 프라이빗 액세스 설정을 Account 수준으로 두면 된다
    • D. 불가능하다. 컨텍스트 기반 인그레스와 IP 액세스 목록은 동시에 설정할 수 없다
    정답과 해설

    정답: B — 인바운드 네트워크 페이지는 IP 액세스 목록이 인터넷 트래픽에만 적용되며 PrivateLink로 들어오는 사설 IP를 막지 못한다고 설명합니다. 사설 경로를 제한하려면 프라이빗 액세스 설정을 ENDPOINT 수준으로 바꾸거나 컨텍스트 기반 인그레스를 씁니다. A와 C는 이 적용 범위와 다르고, D는 컨텍스트 기반 인그레스와 IP 액세스 목록을 둘 다 적용해 하나라도 거부하면 거부한다는 본문과 반대입니다.

    근거: 인바운드 네트워크 접근 — IP 액세스 목록 (IP access lists)

    10. 서버리스 아웃바운드 정책을 강제 적용하기 전에 해야 할 일은? (수준 300)¶

    • A. 새 정책을 바로 강제로 적용하고, 장애가 나면 그때 Full Access로 되돌린다
    • B. 새 정책을 dry-run으로 평가해 아웃바운드 기록에서 차단될 호출을 확인하고, 허용 목록을 보완한 뒤 강제 적용한다
    • C. 서버리스 컴퓨트는 이그레스 제어 대상이 아니므로 클래식 방화벽만 설정하면 된다
    • D. 한 워크스페이스에 여러 네트워크 정책을 동시에 연결해 합집합으로 적용한다
    정답과 해설

    정답: B — 본문은 새 정책을 dry-run으로 먼저 평가하고, 아웃바운드 기록에서 차단될 호출을 확인해 허용 목록에 추가한 뒤 강제 적용하는 순서를 권장합니다. A는 정상 워크로드가 장애로 드러난다는 점에서 본문의 주의사항과 반대입니다. C는 노트북, 잡, SQL 웨어하우스 등이 적용 대상이라는 본문과 다르고, D는 한 워크스페이스에 한 번에 한 정책만 연결할 수 있다는 본문과 다릅니다.

    근거: 서버리스 이그레스와 NCC — 적용 순서 예시

    실무 체크리스트¶

    이 장의 내용을 실제 환경에 적용할 때 확인할 항목입니다.

    • 계정 관리자와 워크스페이스 관리자의 변경 권한을 표로 나눠 정의했다 — 보안 모델 개요 — 2.2 계정과 워크스페이스의 역할
    • 퇴사 처리 순서를 정했다. IdP에서 비활성화하고, 다음 동기화 뒤 개인 액세스 토큰을 폐기한다 — ID와 접근 — 자동 ID 관리 (AIM)
    • 잡은 서비스 프린시펄로 실행하고, 실행자에게 Service Principal User 역할을 명시적으로 줬다 — ID와 접근 — 3.1 서비스 프린시펄 만들고 배정하기
    • 토큰 보고서로 PAT 사용 현황을 보고, 최대 수명 설정을 점검했다 — 인증과 토큰 — 최대 수명 설정
    • 네트워크를 바꾸기 전에 사설 경로를 검증하고, 공개 접근 설정은 나중에 끄도록 순서를 잡았다 — 인바운드 네트워크 접근 — 5. 주의사항
    • 서버리스 아웃바운드 정책은 dry-run으로 기록을 확인한 뒤 강제 적용하도록 계획했다 — 서버리스 이그레스와 NCC — 적용 순서 예시
    • 고객 관리 키의 적용 범위를 관리형 서비스, 워크스페이스 스토리지, Unity Catalog로 나눠 문서화했다 — 암호화·시크릿·컴플라이언스 — 고객 관리 키 (Customer-managed keys)
    • 감사 테이블은 감사 담당 그룹으로 조회 권한을 한정하고, 보존 기간이 요구 기간보다 짧은 테이블을 따로 보완했다 — 감사 로그와 시스템 테이블 — 활성화 조건
    • 예산 임계값과 알림 수신자를 정했고, 차단은 Unity Gateway 예산에서만 쓴다는 한계를 알고 있다 — 비용 관리 — 예산 (Budgets)
    • 운영 점검 주기(매주·매월·분기)와 점검 기록 방식을 정했다 — 워크스페이스 운영 체크리스트 — 점검 주기
