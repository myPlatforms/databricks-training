    Genie Agents 신뢰도 높이기¶

    기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 300

    한눈에 보기¶

    Genie는 자연어 질문을 SQL로 바꾸는 생성형 시스템입니다. 공식 문서는 Genie가 비결정적(nondeterministic)이며, 설정이 모호하거나 서로 충돌하면 답이 일관되지 않을 수 있다고 설명합니다. 따라서 Genie Agent의 품질은 모델이 아니라 설정의 설계 로 결정되는 부분이 큽니다.

    이 페이지는 신뢰도를 올리는 다섯 가지 설계 축을 다룹니다.

    축 설정 항목 목적
    지침 인스트럭션(Instructions) 모든 질문에 공통으로 적용할 규칙
    예제 예제 SQL, 신뢰 자산(Trusted assets) 자주 나오는 질문 패턴을 정확한 SQL로 고정
    메타데이터 테이블·열 설명, 동의어, 값 매칭 현업 용어와 데이터 값을 연결
    지식 저장소 조인 관계, SQL 식(Expression) 반복되는 비즈니스 로직을 정확히 정의
    측정 벤치마크, 모니터링 변경이 정확도를 높였는지 확인

    1. 왜 필요한가¶

    이전 방식의 한계¶

    • 질문마다 Genie가 KPI 정의를 새로 추론하면, 같은 "매출"이 다른 계산식으로 나올 수 있습니다.
    • 인스트럭션에 모든 규칙을 길게 넣으면 규칙끼리 충돌하고, 모델이 일부를 무시할 수 있습니다.
    • 정확도를 확인하는 기준이 없으면 설정을 바꿔도 좋아졌는지 알 수 없습니다.

    Genie 문서는 맥락을 알맞은 위치에 두라고 권장합니다. 모든 질문에 적용할 규칙은 일반 인스트럭션에, 일부 질문에만 적용할 맥락은 예제 SQL, 함수, 테이블·열 설명에 두는 방식입니다. 정확한 계산식은 텍스트 지침보다 SQL 식으로 정의하는 편이 Genie가 그대로 적용합니다.

    2. 어떻게 동작하는가¶

    맥락이 답에 쓰이는 방식¶

    Genie는 답을 만들 때 다음 맥락을 조합합니다. 앞 페이지에서 본 목록과 같습니다.

    • UC 테이블 메타데이터(이름, 설명, 기본 키·외래 키 관계)
    • 열 이름과 설명
    • 지식 저장소(에이전트 전용 메타데이터). UC 메타데이터는 바꾸지 않음
    • 예제 SQL. 질문과 관련 있는 예제를 골라 참고
    • SQL 함수
    • 인스트럭션
    • 대화 이력. 토큰 한도 때문에 가장 오래된 부분이 잘릴 수 있음

    공식 문서는 벤치마크가 평가만을 위한 것이며 Genie의 맥락을 개선하지 않는다고 명시합니다. 벤치마크는 설정을 측정하는 도구이지, 설정을 자동으로 고쳐 주지 않습니다.

    3. 어떻게 쓰는가¶

    3-1. 인스트럭션 (한도 100개)¶

    공식 문서 기준으로 인스트럭션 한도는 에이전트당 100개 입니다. 세는 단위는 다음과 같습니다.

    • 예제 SQL 하나
    • SQL 함수 하나
    • 일반 인스트럭션(General instructions) 블록 전체 하나

    일반 인스트럭션에는 모든 프롬프트에 적용되는 맥락만 씁니다. 공식 예시는 회계 연도 정의, 출력 언어, 반올림 규칙, 숫자 형식입니다. 일부 질문에만 필요한 맥락은 예제 SQL, 함수, 테이블·열 설명에 옮깁니다.

    인스트럭션은 충돌과 모호함이 없는지 검토하십시오. 문서는 모순이 있으면 일관되지 않은 답의 위험이 커진다고 설명합니다.

    3-2. 예제 SQL과 신뢰 자산¶

    예제 SQL은 질문과 쿼리를 짝지어 Genie가 같은 패턴을 따르도록 합니다. 문서의 작성 원칙은 다음과 같습니다.

    • 예제 질문은 사용자가 실제로 쓰는 표현 으로 씁니다. 그 표현을 예제 제목으로 씁니다.
    • 일반적인 쿼리보다 조직 고유의 로직 에 집중합니다. 예: 이 회사에서 "파이프라인"이 무엇을 뜻하는지.
    • 사용 지침(Usage guidance)으로 언제 이 예제가 적용되는지 설명합니다.

    매개변수 있는 쿼리¶

    예제 SQL에는 실행 시점에 입력을 받는 매개변수(parameter)를 넣을 수 있습니다. Add parameter 를 누르거나 본문에 :parameter_name 형태로 씁니다. 지원되는 데이터 타입은 String, Date, Date and Time, Decimal, Integer 입니다. 타입이 맞지 않으면 결과가 부정확할 수 있다고 문서가 경고합니다.

    -- 예시: 예제 SQL 본문에 매개변수를 넣는 형태
SELECT
  region,
  SUM(amount) AS total_amount
FROM main.sales.orders
WHERE order_date >= :start_date
GROUP BY region

    위 예시에서 :start_date는 예제 SQL 설정에서 Date 타입으로 정의합니다. 테이블 이름 main.sales.orders는 설명을 위한 가상의 이름입니다. 실제 워크스페이스에서는 본인이 접근할 수 있는 테이블로 바꾸십시오.

    신뢰 자산(Trusted assets)¶

    신뢰 자산은 매개변수 있는 쿼리 와 UC SQL 함수 입니다. Genie가 신뢰 자산을 쓰면 해당 답은 검증된 답(verified answer)으로 표시됩니다.

    • 신뢰 자산을 추가하거나 제거하려면 최소 CAN EDIT 권한이 필요합니다.
    • 에이전트 사용자가 신뢰 자산의 UC SQL 함수를 쓰려면 그 함수에 EXECUTE 권한이 필요합니다.

    주의 신뢰 자산의 UC SQL 함수를 쓰는 사용자에게는 EXECUTE 권한이 빠지기 쉽습니다. 권한이 없으면 해당 답이 실패합니다. 함수 권한은 06장 권한 모델에서 확인하십시오.

    3-3. 테이블과 열 메타데이터¶

    메타데이터 설정은 Configure > Sources 에서 합니다.

    설정 동작
    테이블 Description 편집 가능. Reset 으로 UC의 설명을 복원
    열 Descriptions 열 설명을 에이전트에 추가
    열 Synonyms 현업이 쓰는 이름을 동의어로 추가
    열 Hide 불필요하거나 혼동을 주는 열을 Genie 맥락에서만 숨김. 기반 테이블이나 권한은 바뀌지 않음
    Format assistance 대표 값을 샘플링해 형식을 맞춤
    Entity matching 문자열 열의 고유 값을 저장해 사용자 표현을 실제 값에 연결
    Refresh prompt matching 값이 바뀌었을 때 값 목록을 새로 고침

    Entity matching 의 수치 한도는 다음과 같습니다.

    항목 한도
    값 매칭 대상 문자열 열 에이전트당 최대 120개
    열당 저장 값 최대 1,024개
    값 하나의 길이 최대 127자

    예시: 사용자가 "Florida"라고 물으면, 저장된 값 FL과 연결하려면 주 코드 열에 Entity matching을 켭니다. 공식 문서도 주(state) 코드 같은 범주형 문자열 열에 켜라고 권장합니다.

    필터와 마스크가 있는 테이블의 주의점은 다음과 같습니다.

    • 행 필터 가 있는 테이블은 프롬프트 매칭에서 테이블 전체가 제외 됩니다.
    • 열 마스크 가 있는 열은 마스크된 열만 제외됩니다.
    • 행 필터가 걸린 테이블을 참조하는 뷰나 동적 뷰는 Entity matching을 끄십시오.

    참고 행 필터와 열 마스크는 06장에서 설계합니다. 여기서는 Genie 맥락에서 어떻게 빠지는지만 확인합니다.

    3-4. 지식 저장소 (한도 200개)¶

    지식 저장소는 에이전트 전용 메타데이터입니다. 한도는 에이전트당 200개 스니펫 입니다.

    • 세는 항목: 테이블 설명, 조인 관계, SQL 식
    • 세지 않는 항목: 인스트럭션, 예제 쿼리, 함수, 열 설명, 프롬프트 매칭 설정

    조인 관계(join relationship)는 JOIN 조건과 관계 유형을 정의합니다. 관계 유형은 Many to one, One to many, One to one 세 가지입니다. 복잡한 조건은 SQL 식으로 저장할 수 있습니다.

    SQL 식 은 세 종류입니다.

    종류 설명 예시 성격
    Filters 불리언 조건 대형 주문
    Measures 집계 KPI 승률
    Fields 행마다 계산되는 속성 거래 규모 구간

    각 식은 이름(name), 코드(code), 동의어(synonyms), 지침(instructions)을 가집니다.

    권장 정확한 비즈니스 규칙(KPI 계산식, 임계값, 분류)은 텍스트 인스트럭션보다 SQL 식 으로 정의하십시오. 문서는 Genie가 SQL 식을 적은 그대로 적용한다고 설명합니다.

    3-5. 지식 마이닝 제안¶

    공식 문서는 지식 마이닝(knowledge mining) 제안을 검토하라고 권장합니다.

    • 기본 키와 외래 키는 조인으로 자동 저장 됩니다.
    • Genie는 작성자가 긍정 평가한 대화나 다운로드한 결과에서 식과 조인을 제안합니다.

    제안은 수락 전에 검토하십시오. 자동 저장되는 조인이 실제 비즈니스 관계와 다를 수 있습니다.

    3-6. 벤치마크¶

    벤치마크는 질문과 기대 답을 모아 두고, 설정을 바꿀 때마다 정확도를 측정하는 도구입니다. 공식 모니터링 문서가 설명하는 내용은 다음과 같습니다.

    항목 내용
    한도 에이전트당 500개 질문
    질문 표현 같은 질문을 2~4가지 표현으로 씀
    정답 SQL 질문마다 SQL answer 를 넣을 수 있음. 채팅 모드는 이를 기준으로 정확도를 자동 판정
    평가 메모 evaluation note. Agent mode의 LLM 판정기(judge)에게 기준을 알려 줌
    실행 모드 실행할 때마다 Chat 또는 Agent 중에 고름. 질문 생성 시점이 아님

    채팅 모드의 판정 규칙은 다음과 같습니다.

    • Genie의 SQL 결과가 정답 SQL 결과와 일치하면 Good 입니다. 행 순서가 달라도, 숫자가 유효숫자 4자리까지 맞으면 일치로 봅니다.
    • 오류, 빈 결과, 추가 열, 다른 단일 셀 결과는 Bad 입니다.
    • 정답 SQL이 없거나 정확히 맞지 않으면 Manual review needed 로 표시됩니다.
    • 비교는 최대 5,000행 까지 합니다.

    Agent mode는 LLM 판정기가 평가 메모에 맞는지 보고 Good을 줍니다.

    실행 결과는 Evaluations 탭에 실행 시각, 실행 상태, 정확도 점수, 생성자와 함께 나열됩니다. 실행 상태는 completed, paused, unsuccessful 등입니다. 실행 상세는 1주일 간 보관된다고 문서에 나옵니다.

    주의 벤치마크 실행 상세가 1주일 뒤 사라진다는 점을 운영 절차에 넣으십시오. 장기 추세가 필요하면 결과를 별도로 기록해 두어야 합니다. 이 장은 보관 방식을 추가로 확인하지 않았습니다.

    3-7. 모니터링¶

    Monitor 탭은 사용자가 한 질문과 답을 보여 줍니다. 시간, 평가, 사용자, 상태로 걸러 볼 수 있고, 항목을 열어 전체 대화를 읽을 수 있습니다.

    • 사용자는 응답을 Yes, Fix it, Request review 로 평가할 수 있습니다. 표시된 항목은 Monitor 페이지에 모입니다.
    • Weekly digest 는 메시지 양, 활성 사용자, 좋아요·싫어요 피드백을 보여 줍니다.
    • Analyze Agent Usage 는 Genie Code를 써서 최근 6개월 의 활동을 요약합니다. 2026-09-17 릴리즈 노트는 작성자가 Monitor 탭에서 최대 6개월의 에이전트 활동을 요약할 수 있다고 기록합니다.
    • 대화 공개 범위는 두 가지입니다. Reviewable by agent managers 는 관리자가 전체 대화를 검토할 수 있고, Private 은 프롬프트만 보입니다. 기능이 켜지기 전에 만들어진 대화는 계속 Private입니다.
    • CAN MANAGE 권한자는 Monitor 탭에서 대화를 삭제할 수 있고, 삭제하면 모든 사용자에게서 사라집니다.

    주의 대화 공개 범위 설정을 확인하십시오. 관리자 검토가 가능한 대화에는 사용자의 질문 전문이 들어갑니다. 개인정보가 들어가는 질문을 다루는 에이전트는 공개 범위를 정책에 맞게 정하십시오.

    4. 트레이드오프¶

    • 인스트럭션은 쉽지만 한도와 충돌 위험이 있습니다. 100개 한도를 일반 인스트럭션으로 채우면 나중에 고칠 여지가 없습니다. 예제 SQL과 SQL 식으로 나누는 편이 관리에 낫습니다.
    • 신뢰 자산은 정확하지만 준비 비용이 큽니다. 질문마다 SQL을 검증해야 합니다. 반복되는 질문에만 쓰십시오.
    • Entity matching은 답을 개선하지만 값 목록을 저장합니다. 값이 자주 바뀌면 새로 고침이 필요하고, 민감한 값이 들어 있으면 검토가 필요합니다.
    • 벤치마크는 측정 도구일 뿐입니다. 점수를 올리려고 벤치마크에 맞춰 설정하면, 실제 질문에서는 나아지지 않을 수 있습니다.
    • Agent mode 판정은 LLM 판정기가 평가 메모에 맞는지 보는 방식입니다. 채팅 모드의 SQL 결과 비교와 판정 기준이 다릅니다. 중요한 질문은 정답 SQL을 함께 넣어 채팅 모드에서도 비교할 수 있게 해 두십시오.

    5. 주의사항¶

    • 일반 인스트럭션에는 공통 규칙만 씁니다. 질문 한두 개에만 맞는 규칙을 넣지 않습니다.
    • 정확한 계산식은 SQL 식으로 정의합니다. 텍스트 설명보다 정확합니다.
    • 신뢰 자산의 EXECUTE 권한을 확인합니다. 에이전트 사용자 그룹에 함수 실행 권한을 주었는지 점검하십시오.
    • 행 필터와 열 마스크가 있는 테이블은 프롬프트 매칭을 확인합니다. 테이블 전체가 빠질 수 있습니다.
    • 벤치마크를 변경 전후로 돌립니다. 설정을 바꾸면 벤치마크를 다시 실행하는 것을 변경 절차로 삼으십시오.
    • 영어 프롬프트가 기본 경로입니다. 문서는 비영어 프롬프트가 영어 시스템 프롬프트로 감싸져 응답이 영어로 나올 수 있다고 설명합니다.
    • Flash 리전 제약을 확인합니다. 문서는 미국·EU 외 워크스페이스에서 Flash가 cross-Geo 처리를 요구한다고 설명합니다. 데이터 거주 요구가 있으면 설계 전에 확인하십시오.
    • 라벨을 확인합니다. Flash(Beta), Inspect(Public Preview), Genie Ontology 기본 활성화(Public Preview, 2026-08-06 릴리즈 노트)는 기능별로 다릅니다.
