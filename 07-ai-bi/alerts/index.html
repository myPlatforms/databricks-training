    알림(Alerts)¶

    기준일: 2026-10-29 · 근거: 공식 문서

    한눈에 보기¶

    Databricks SQL 알림(Alerts)은 쿼리 결과를 정해진 주기로 확인하고, 조건을 만족하면 알림 대상(notification destination)에 통지하는 기능입니다. 알림마다 자기만의 쿼리가 있고, 그 쿼리 결과에 조건을 겁니다. 평가할 때마다 상태가 정해집니다.

    상태 의미
    OK 조건을 만족하지 않음
    TRIGGERED 조건을 만족함
    ERROR 평가 중 오류

    공식 문서는 기존 알림의 UNKNOWN 상태를 최신 알림에서 지원하지 않는다고 명시합니다. 전환 기간에는 최신 알림과 기존(legacy) 알림이 함께 동작할 수 있습니다. 기존 알림 동작은 "What are legacy alerts?" 페이지에서 확인합니다.

    참고 2026-08~10월 AI/BI 릴리즈 노트에는 알림 자체의 기능 변경 항목이 없습니다. 다만 2026-08-10 릴리즈 노트는 알림 시스템 테이블(system.alert)이 Public Preview라고 발표했습니다. 이 페이지의 내용은 공식 알림 문서를 기준으로 합니다.

    1. 왜 필요한가¶

    이전 방식의 한계¶

    • 매출이 기준 아래로 떨어졌는지 매일 대시보드를 열어 확인하는 일은 사람이 빠지면 멈춥니다.
    • 대시보드는 사람이 보는 도구입니다. 임계값을 넘었을 때 먼저 알려 주는 역할은 하지 못합니다.
    • 쿼리 결과를 스크립트로 확인하려면 스케줄러와 메신저 연동을 직접 만들어야 합니다.

    알림은 쿼리, 조건, 스케줄, 알림 대상을 한 객체에 묶어, 조건이 맞을 때만 통지를 보냅니다. 문서는 알림으로 할 수 있는 일을 다음 범주로 소개합니다.

    범주 예
    비즈니스 지표 메트릭 뷰(Metric view)의 측정값을 이름으로 참조해 임계값 감시
    데이터 품질·이상 데이터 품질 모니터와 이상 탐지를 짝지어 분포 변화나 프로파일 변화를 통지
    사용량·비용 서버리스 과금이나 수집 파이프라인 비용 시스템 테이블에 알림
    웨어하우스·쿼리 상태 웨어하우스 이벤트나 쿼리 이력으로 느린 쿼리, 실패 세션, 용량 문제 감지
    감사·보안 감사 로그 쿼리로 비정상 활동 감지
    에이전트 품질 에이전트 품질 지표로 실패 징후 감지
    워크플로 연계 Lakeflow Jobs의 SQL 알림 태스크로 실행해 후속 태스크를 분기

    2. 어떻게 동작하는가¶

    구성 요소¶

    공식 문서가 설명하는 알림의 구성 요소는 다음과 같습니다.

    요소 설명
    쿼리 알림마다 고유한 쿼리를 새 알림 편집기에서 씁니다. 쿼리는 알림의 일부입니다
    조건 쿼리 결과의 열(또는 집계 값)을 임계값과 비교하는 규칙
    스케줄 쿼리를 정해진 주기로 실행하고, 실행마다 조건을 평가
    알림 대상 상태가 바뀔 때 통지를 받을 대상. 문서는 웹훅 대상을 설명
    평가 이력 과거 평가 결과를 알림 이력에서 확인

    조건의 구성¶

    웹훅 페이로드 명세에서 확인되는 조건 필드는 다음과 같습니다. 알림 설정이 이 값을 정합니다.

    필드 의미
    source 조건이 평가할 쿼리 결과 열과 집계
    comparison_operator 비교 연산자 (예: GREATER_THAN, EQUAL, IS_NULL)
    threshold 비교 대상 값 또는 결과 열
    empty_result_state 쿼리가 행을 반환하지 않을 때 쓸 상태. 설정하지 않으면 필드가 생략됨
    notification.seconds_to_retrigger 재통지 간격(초)
    notification.notify_on_ok OK 상태 전환도 통지할지 여부
    notification.subscriptions[].destination_id 알림 대상 ID

    평가 흐름¶

    1. 스케줄에 따라 알림의 쿼리가 실행됩니다.
    2. 쿼리 결과에 조건을 적용해 OK, TRIGGERED, ERROR 중 하나로 평가합니다.
    3. 상태가 바뀌면 알림 대상에 통지합니다. 웹훅 대상은 상태 변화 후 JSON 페이로드 를 받습니다.
    4. 평가 결과는 이력에 남습니다.

    웹훅 페이로드¶

    웹훅은 다음 최상위 필드를 가진 JSON을 받습니다. 아래는 문서 예제를 줄여 옮긴 것입니다. 식별자와 이름은 문서의 가상 값입니다.

    {
  "event": "alert_state_change",
  "url_base": "https://<workspace-url>/sql?o=1234567890123456",
  "alert": {
    "title": "Alert \"Daily revenue\" changed status to TRIGGERED",
    "description": "Daily revenue exceeded the configured threshold.",
    "alert": {
      "id": "9876543210987654",
      "name": "Daily revenue",
      "owner": { "id": 2468013579246801, "name": "Alex Smith", "email": "alex.smith@example.com" },
      "query_text": "SELECT SUM(revenue) AS total_revenue FROM main.sales.daily",
      "warehouse_id": "4b9b953939869799",
      "evaluations": [
        {
          "source": { "name": "total_revenue", "aggregation": "AGGREGATION_UNSPECIFIED" },
          "comparison_operator": "GREATER_THAN",
          "threshold": { "value": { "double_value": 100000.0 } },
          "state": "TRIGGERED"
        }
      ]
    }
  }
}

    주의 페이로드에는 SQL 쿼리 원문, 알림 소유자의 이름과 이메일, 사용자 정의 알림 내용이 들어갑니다. 수신 엔드포인트를 보호하고, 저장된 페이로드 접근을 제한하십시오. 문서는 필드가 없을 수 있으므로 수신 측이 알 수 없는 필드를 무시하고 선택 필드의 부재를 처리하도록 권장합니다.

    쿼리 재사용의 제약¶

    알림을 만들 때 이미 저장된 SQL 쿼리를 재사용할 수 없습니다. 공식 문서는 알림이 자기 쿼리 정의를 가진다고 설명합니다. 같은 쿼리를 대시보드와 알림이 함께 쓰고 싶으면 쿼리를 두 번 작성하거나, 쿼리 내용을 동일하게 맞추는 방식으로 관리해야 합니다.

    메트릭 뷰 측정값에 걸기¶

    메트릭 뷰 소비 문서는 알림을 메트릭 뷰의 측정값을 모니터링하고 임계값을 넘으면 통지를 보내는 소비 경로로 설명합니다. 알림 쿼리에서는 메트릭 뷰를 정규화된 이름(완전한 이름)으로 참조합니다. 측정값 조회 문법의 자세한 규칙은 메트릭 뷰 소비하기: 대시보드·Genie Agent에서 쓰기를 참고하십시오.

    알림 이력 시스템 테이블¶

    테이블 내용 상태
    system.alert.alerts 모든 알림의 구성 (정의 감사용) Public Preview (2026-08-10 릴리즈 노트)
    system.alert.alert_evaluation_history 평가 한 번당 한 행 Public Preview (2026-08-10 릴리즈 노트)

    3. 어떻게 쓰는가¶

    기본 절차¶

    공식 문서 기준으로 알림을 만드는 흐름은 다음과 같습니다. 화면 위치와 메뉴 이름은 대상 워크스페이스 버전에 따라 다를 수 있으니 공식 문서의 절차 페이지에서 확인하십시오. 절차 페이지는 고급 설정과 알림 템플릿 사용자 지정까지 다룹니다.

    1. 알림 편집기를 열고, 알림 전용 쿼리를 작성합니다.
    2. 쿼리 결과에 대한 조건(연산자·임계값)을 정의합니다.
    3. 평가 스케줄을 정합니다.
    4. 알림 대상(예: 웹훅)을 연결합니다.
    5. 이력에서 첫 평가가 OK 또는 TRIGGERED로 끝나는지 확인합니다.

    쿼리는 조건에 필요한 최소한의 행과 열을 반환하도록 작성하십시오. 알림은 결과에 조건을 적용하는 것이므로, 쿼리가 무거우면 스케줄마다 그 비용이 듭니다.

    활용 예: 임계값 알림 쿼리¶

    조건을 쓰기 쉽도록, 한 개의 숫자 열을 반환하는 쿼리로 시작합니다. 아래는 웹훅 예제와 같은 형태의 예시입니다. 실제 테이블 이름은 여러분의 카탈로그에 맞게 바꾸십시오.

    SELECT SUM(revenue) AS total_revenue
FROM main.sales.daily
WHERE sale_date = current_date() - INTERVAL 1 DAY;

    이 쿼리 결과의 total_revenue에 비교 연산자(예: 기준 미만을 뜻하는 연산자)와 기준 금액을 걸면 매출 하락을 감시할 수 있습니다. 연산자 이름은 알림 편집기에서 고르며, 문서 예제에 나온 이름은 GREATER_THAN, EQUAL, IS_NULL입니다. 결과가 행이 없을 때 상태를 정하는 empty_result_state도 함께 정하십시오.

    Lakeflow Jobs의 SQL 알림 태스크¶

    알림을 Lakeflow Jobs의 SQL 알림 태스크 로 추가하면, 파이프라인 트리거에 맞춰 조건 검사를 실행하고 후속 태스크가 결과에 따라 분기할 수 있습니다. 태스크는 평가 상태를 태스크 출력 값으로 반환하므로, 하위 태스크는 그 값으로 분기합니다. 이 방식은 임계값 검사 뒤에 여러 시스템에 걸친 후속 작업을 이어 붙일 때 쓰는 패턴입니다. 자세한 분기 방법은 파라미터·태스크 값·조건 분기를 참고하십시오.

    참고 릴리즈 노트에 따르면 SQL 알림 태스크는 compliance security profile이 켜진 워크스페이스에서 기본으로 제공됩니다.

    공유, 권한, 소유권¶

    • 권한: 알림 권한은 누가 알림을 보고(view), 실행하고(run), 편집할지(edit) 정합니다. 공유 대화상자에서 그룹이나 사용자를 고르고 권한 수준을 지정합니다. 권한 수준의 세부 정의는 Alerts ACLs 페이지에서 확인합니다.
    • 소유권: 알림을 저장하면 저장한 사용자가 소유자가 됩니다. 소유자가 워크스페이스에서 제거되면 알림에 소유자가 없게 되며, 워크스페이스 관리자가 다른 사용자에게 소유권을 이전할 수 있습니다. 권한 API로도 이전할 수 있습니다.
    • Git 폴더: 알림을 Databricks Git 폴더에 두면 Git으로 변경을 추적합니다. 복제된 알림은 사용자가 상호작용하기 전까지 목록이나 API에 나타나지 않으며, 스케줄이 일시 중지되어 사용자가 명시적으로 재개해야 합니다.

    4. 트레이드오프¶

    • 알림은 간단하지만 쿼리를 따로 관리해야 합니다. 대시보드의 데이터셋을 재사용할 수 없으므로, 같은 계산이 두 곳에 생길 수 있습니다.
    • 웹훅은 어디든 연결할 수 있지만 페이로드 형식을 직접 처리해야 합니다. 위 예시처럼 필드 일부는 조건에 따라 생략됩니다. 수신 측은 이를 전제로 짜야 합니다.
    • 알림 대상 종류: 문서는 알림 대상을 notification destination으로 설명하고 웹훅 페이로드를 자세히 다룹니다. 이메일이나 Slack 같은 다른 대상 종류가 가능한지는 이 페이지에서 확인하지 않았습니다. 대상 워크스페이스의 알림 대상 설정에서 확인하십시오.
    • 레거시 알림과의 차이: 아래 표를 기준으로 판단합니다.
    항목 최신 Databricks SQL 알림 레거시 알림
    쿼리 재사용 저장된 SQL 쿼리를 재사용할 수 없고, 알림마다 쿼리를 가짐 문서에 재사용 항목 없음 (레거시 페이지 참고)
    상태 값 OK, TRIGGERED, ERROR UNKNOWN을 포함
    공존 전환 기간에 레거시 알림과 나란히 사용 가능 —
    목록 알림 목록 기본 탭 "Alerts" "Legacy alerts" 탭

    언제 쓰지 않는가¶

    • 실시간 스트리밍 이벤트에 반응해야 하는 경우. 알림은 스케줄마다 쿼리를 실행하는 방식입니다. 실시간 처리는 스트리밍 파이프라인이나 Structured Streaming을 검토합니다.
    • 임계값 검사가 아니라 여러 시스템에 걸친 복잡한 워크플로우를 실행해야 하는 경우. 이때는 Lakeflow Jobs에서 조건 분기를 쓰는 편이 맞습니다. Lakeflow Jobs 태스크와 트리거를 참고하십시오.

    5. 주의사항¶

    • 알림이 실행되는 자격 증명을 확인합니다. 공식 알림 문서는 쿼리가 소유자의 권한으로 도는지, 다른 사용자의 권한으로 도는지 명시하지 않습니다. 소유자가 바뀌거나 권한이 바뀌었을 때 알림이 실패하지 않는지, 운영 전에 테스트하십시오.
    • ERROR 상태를 감시합니다. 조건이 맞지 않아 OK인 것과 쿼리 실패로 ERROR인 것은 다릅니다. ERROR를 OK로 착각하면 장애를 놓칩니다.
    • UNKNOWN 상태에 기대지 않습니다. 공식 문서는 최신 알림이 이 상태를 지원하지 않는다고 명시합니다. 기존 알림을 옮길 때 이 상태를 보고 있던 로직을 고치십시오.
    • 쿼리 재사용 제약을 설계에 넣습니다. 저장된 쿼리를 알림에 바로 붙일 수 없습니다.
    • 전환 기간의 혼재를 확인합니다. 최신 알림과 기존 알림이 함께 있을 수 있으므로, 목록에서 어떤 것이 기존 알림인지 구분하십시오.
    • 알림 대상의 소유자를 정합니다. 웹훅 주소가 바뀌면 통지가 끊깁니다. 대상 관리 담당자를 정하십시오.
    • Git 복제 후 재개: Git 폴더로 복제한 알림은 스케줄이 멈춰 있습니다. 재개할 때 조건과 대상이 의도와 맞는지 확인하십시오.
    • 소유자 이탈: 소유자가 워크스페이스에서 제거되면 알림이 소유자 없이 남습니다. 정기적으로 소유자 없는 알림을 점검하고 소유권을 이전하십시오.
