    퀴즈와 체크리스트¶

    기준일: 2026-10-29 · 근거: 이 장 본문 · 수준: 100~300

    이 장에서 다룬 내용을 확인하는 문제입니다. 정답을 펼치면 해설과 근거 페이지로 가는 링크가 있습니다.

    퀴즈¶

    1. 에이전트를 단일 모델 호출과 구분하는 핵심 특징은 무엇인가? (수준 100)¶

    • A. 모델이 한 번의 호출로 모든 답을 끝낸다.
    • B. 모델이 도구를 골라 호출하고, 결과를 보고 다음 행동을 정하는 반복 루프를 가진다.
    • C. 모든 데이터를 프롬프트에 미리 넣어 두고 답한다.
    • D. 사람이 매 단계마다 다음 행동을 직접 지정한다.
    정답과 해설

    정답: B — 본문은 에이전트를 모델이 도구를 골라 호출하고, 그 결과를 보고 다음 행동을 정하는 반복 루프로 설명합니다. 모델은 다음에 무엇을 할지를 정하고, 실제 실행은 도구가 맡습니다. A는 단일 호출의 한계이고, C는 모델이 데이터를 모른다는 본문 설명과 어긋납니다. D는 본문이 말하는 구조와 반대입니다.

    근거: AI 에이전트란 무엇인가 — 왜 필요한가

    2. 에이전트 문서의 용어 중 세션(session)과 메모리(memory)에 대한 설명으로 옳은 것은? (수준 100)¶

    • A. 세션과 메모리는 같은 저장소이며, 세션을 지우면 메모리도 함께 지워진다.
    • B. 세션은 한 번의 상호작용 또는 대화의 상태를, 메모리는 여러 대화에 걸쳐 회상할 사실이나 결정을 담는다.
    • C. 메모리는 트레이스와 같은 말이며 MLflow 실험에만 남는다.
    • D. 세션은 여러 대화에 걸쳐 쌓이고, 메모리는 한 상호작용이 끝나면 사라진다.
    정답과 해설

    정답: B — 본문은 세션을 한 번의 상호작용 상태(주로 대화 기록)로, 메모리를 여러 대화에 걸쳐 회상할 사실, 선호, 결정으로 구분합니다. 두 저장소는 독립적이어서 세션을 지워도 메모리는 남는다고 설명합니다. A는 독립 저장소라는 본문 설명과 어긋납니다. C는 트레이스에 대한 설명이고, D는 수명이 뒤바뀌었습니다.

    근거: AI 에이전트란 무엇인가 — 헷갈리기 쉬운 용어

    3. 고정된 RAG와 에이전트를 구분하는 기준으로 본문이 제시하는 것은? (수준 100)¶

    • A. 사용하는 모델의 크기
    • B. 검색 단계가 고정되어 있는지, 즉 검색을 할지와 어떤 인덱스를 고를지를 모델이 정하는지
    • C. 임베딩 차원의 수
    • D. 결과를 화면에 보여 주는 방식
    정답과 해설

    정답: B — 본문은 RAG와 에이전트의 차이가 검색 단계가 고정되어 있는지에 있다고 설명합니다. 고정 RAG는 검색 후 생성의 순서가 정해져 있고, 에이전트는 검색 여부, 인덱스 선택, 결과 부족 시 재검색을 모델이 정합니다. 두 방식을 섞을 수도 있다고 덧붙입니다. A, C, D는 본문이 구분 기준으로 제시한 내용이 아닙니다.

    근거: AI 에이전트란 무엇인가 — 언제 쓰는가

    4. 새로 문서 기반의 저코드 에이전트를 만들려고 합니다. 레거시 제품 Knowledge Assistant 대신 본문이 안내하는 경로는? (수준 200)¶

    • A. Supervisor Agent로 여러 에이전트를 묶는다.
    • B. 저코드는 Genie Agents, 코드로 만드는 에이전트는 Agent Bricks CLI를 쓴다.
    • C. Model Serving 커스텀 에이전트로 배포한다.
    • D. 레거시 에이전트 서버를 새로 구현한다.
    정답과 해설

    정답: B — 본문은 Knowledge Assistant가 레거시이며, 새 저코드 에이전트에는 Genie Agents, 코드로 만드는 새 에이전트에는 Agent Bricks CLI를 쓰라고 안내합니다. A의 Supervisor Agent도 레거시이고 새 시스템에 권장되지 않습니다. C와 D는 본문이 레거시로 표시한 경로입니다.

    근거: Databricks 에이전트 제품 지도 — 레거시와 현재 제품의 구분

    5. 에이전트가 사용자별 Unity Catalog 권한이 반영된 결과를 내야 하는 MCP 도구를 Agent Bricks CLI 프로젝트에 붙이려고 합니다. 맞는 인증 설정은? (수준 200)¶

    • A. auth = "app"으로 두어 앱 서비스 프린시펄로 실행한다.
    • B. auth = "user"로 두어 요청한 사용자의 권한으로 실행한다.
    • C. 도구 인증을 생략하면 자동으로 사용자 권한이 적용된다.
    • D. PAT를 발급해 도구 설정에 넣는다.
    정답과 해설

    정답: B — 본문은 도구의 auth 값이 user이면 요청한 사용자의 권한으로 실행되고, app이면 앱 서비스 프린시펄로 실행된다고 설명합니다. 사용자별 권한이 결과에 반영되어야 하므로 user가 맞습니다. A는 모든 사용자에게 같은 권한이 적용되는 방식입니다. C는 본문이 명시한 기본 동작이 아닙니다. D는 PAT가 Databricks Apps 위의 MCP 서버에 지원되지 않는다는 본문 설명과 어긋납니다.

    근거: Agent Bricks CLI로 에이전트 개발하기 — 도구 추가, 배포와 인증 — 호출 주체 정하기

    6. 정형 데이터가 많은 검색 환경에서 정확한 제품 코드와 개념적인 질문이 함께 들어옵니다. 본문이 시작점으로 권장하는 질의 방식은? (수준 200)¶

    • A. ANN만 쓴다. 벡터 유사도는 정확한 식별자에도 충분하다.
    • B. hybrid를 쓴다. 키워드와 유사도를 결합한다.
    • C. FULL_TEXT만 쓴다. 임베딩을 계산하지 않아야 한다.
    • D. 리랭커를 끄고 결과 수만 늘린다.
    정답과 해설

    정답: B — 본문은 hybrid가 키워드와 유사도를 결합하며, 대부분의 경우 시작점으로 권장된다고 설명합니다. 트레이드오프 표도 정확한 식별자나 고유명사가 많으면 hybrid를 고르라고 안내합니다. A는 벡터만 쓰는 방식으로, 정확한 단어가 중요한 질의에 약하다는 본문 설명과 어긋납니다. C의 FULL_TEXT는 Beta 기능이므로 기본 시작점이 아닙니다. D는 본문의 권장과 관계가 없습니다.

    근거: AI Search와 검색 기반 에이전트 — 질의, AI Search와 검색 기반 에이전트 — 트레이드오프

    7. 운영 중인 에이전트의 품질 개선을 위해 사람이 트레이스를 검토합니다. 피드백과 기대 응답(Expectation)의 차이를 가장 잘 설명한 것은? (수준 200)¶

    • A. 둘은 같은 기능의 두 이름이다.
    • B. 피드백은 실제 출력이 좋은지 판정하는 것이고, 기대 응답은 정답으로 생각하는 출력을 기록하는 것이다.
    • C. 피드백은 프로덕션 모니터링이 자동으로 만들고, 기대 응답은 사람이 지운다.
    • D. 피드백은 도구 호출 순서만 기록하고, 기대 응답은 비용을 기록한다.
    정답과 해설

    정답: B — 본문은 피드백이 실제 출력의 좋고 나쁨을 판정하는 것이고, 기대 응답은 정답으로 생각하는 출력을 기록하는 것이라고 구분합니다. 둘 다 트레이스에 저장됩니다. A는 본문의 구분과 어긋납니다. C와 D는 본문에 없는 설명입니다.

    근거: 트레이싱·평가·피드백 — 어떻게 동작하는가

    8. 결과가 사용자 개인의 행 필터와 열 마스크를 따라야 하는 Databricks Apps 기반 앱을 만들고 있습니다. 본문 기준으로 가장 적절한 인증 모델은? (수준 300)¶

    • A. 앱 권한(App authorization): 앱의 서비스 프린시펄로 모든 사용자가 같은 권한을 공유한다.
    • B. 사용자 권한(User authorization, on-behalf-of): 접속한 사용자의 액세스 토큰을 전달해 사용자의 UC 권한을 따른다.
    • C. 앱 권한과 사용자 권한을 같은 쿼리에서 섞어 쓴다.
    • D. 인증 없이 앱 내부 로직으로 행을 필터링한다.
    정답과 해설

    정답: B — 본문은 사용자 권한 모델에서 Databricks가 사용자의 액세스 토큰을 전달하고, 모든 접근이 그 사용자의 UC 권한을 따르며, 행 필터와 열 마스크도 자동으로 적용된다고 설명합니다. A의 앱 권한은 모든 사용자가 같은 서비스 프린시펄 권한을 공유하므로 사용자별 접근을 강제하지 못합니다. C는 본문이 제시하지 않은 구성입니다. D는 앱이 별도 필터 로직을 가질 필요가 없다고 본문이 말하는 방향과 반대입니다.

    근거: 배포와 인증 — 인증 모델 두 가지

    9. 감사 목적으로 에이전트 호출의 요청과 응답 전체 페이로드를 남겨야 합니다. 본문 기준으로 적합한 기록 수단은? (수준 300)¶

    • A. MLflow 트레이스만 쓴다. 트레이스는 전체 페이로드를 담는다.
    • B. 추론 테이블(Inference tables)을 쓴다. 요청과 응답의 전체 페이로드를 저장한다.
    • C. 속도 제한 설정을 쓴다. 한도 기록이 곧 페이로드가 된다.
    • D. 세션 저장소를 쓴다. 세션은 전체 페이로드의 원본이다.
    정답과 해설

    정답: B — 본문은 추론 테이블이 요청과 응답의 전체 페이로드를 저장하고, MLflow 트레이스는 에이전트 한 번의 실행을 단계별로 기록한다고 구분합니다. 감사와 재현이 목적이면 추론 테이블이 맞습니다. A는 목적이 디버깅과 품질 평가에 가깝습니다. C는 한도를 관리하는 기능이며 페이로드를 저장한다는 설명이 없습니다. D는 세션이 대화 상태를 담는다는 본문 설명과 다릅니다.

    근거: 가드레일·거버넌스·모니터링 — 추론 테이블과 트레이스의 차이

    실무 체크리스트¶

    이 장의 내용을 실제 환경에 적용할 때 확인할 항목입니다.

    • 에이전트를 만들기 전에 단일 호출, 결정적 파이프라인, 고정 RAG로 충분한지 먼저 확인한다 — AI 에이전트란 무엇인가
    • 각 도구의 호출 주체(앱 서비스 프린시펄 또는 호출 사용자)를 설계 문서에 적고, auth 값과 맞는지 확인한다 — 배포와 인증
    • 에이전트 루프의 반복 상한과 타임아웃을 코드에 명시한다 — AI 에이전트란 무엇인가
    • 레거시 Knowledge Assistant나 Supervisor Agent를 쓰고 있다면 현재 제품으로의 전환 계획을 공식 문서와 담당자에게 확인한다 — Databricks 에이전트 제품 지도
    • MCP 도구의 인증 주체(U2M, M2M, PAT 여부)를 호출 경로별로 확인하고, Databricks Apps 위의 MCP 서버에는 PAT를 쓰지 않는다 — 도구: UC 함수와 MCP 서버
    • AI Search 인덱스의 소스 테이블 조건(변경 데이터 피드, 외부 메타데이터 등)을 만들기 전에 확인한다 — AI Search와 검색 기반 에이전트
    • 사용자 토큰을 출력하거나 로그에 남기지 않도록 코드 리뷰 항목에 넣는다 — 배포와 인증
    • 추론 테이블과 트레이스에 들어가는 원문의 보존 기간과 접근 권한을 운영 정책에 맞춰 정한다 — 가드레일·거버넌스·모니터링
    • 프로덕션 모니터링과 리뷰 큐가 Beta인 점을 확인하고, 운영 SLA에 넣기 전에 지원 범위를 검토한다 — 트레이싱·평가·피드백
