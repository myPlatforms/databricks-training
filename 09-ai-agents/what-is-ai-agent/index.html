    AI 에이전트란 무엇인가¶

    기준일: 2026-10-28 · 근거: 공식 문서 · 수준: 100

    왜 필요한가¶

    언어 모델을 한 번 호출하면 입력을 받아 텍스트를 돌려주는 데서 끝납니다. 모델은 회사 데이터를 모르고, 최신 수치를 조회하지 못하고, 결과를 시스템에 기록하지도 못합니다. 질문에 맞는 SQL을 쓰고, 실행하고, 결과를 해석해 다시 답해야 하는 업무는 한 번의 호출로 끝나지 않습니다.

    에이전트는 이 한계를 모델이 도구를 골라 호출하고, 결과를 보고 다음 행동을 정하는 반복 루프 로 풉니다. 모델은 "다음에 무엇을 할지"를 정하고, 실제 실행은 도구가 맡습니다. 도구는 SQL 함수, 검색 인덱스, 외부 서비스의 MCP 서버, 다른 에이전트가 될 수 있습니다.

    Databricks 공식 문서는 에이전트 인프라가 필요한 이유를 다음처럼 요약합니다. 커스텀 에이전트가 운영 환경에서 필요로 하는 기반을 제공한다는 설명입니다. 문서가 나열하는 기반은 Unity Gateway를 통한 모델·MCP 서버·스킬 접근 관리, 에이전트 서버와 Agent Runtime, 관리형 메모리와 세션, 도구와 MCP 서버, MLflow 트레이싱과 평가, Unity Catalog 거버넌스입니다.

    어떻게 동작하는가¶

    구성 요소¶

    에이전트는 네 가지 요소로 나눠 생각하면 설계하기 쉽습니다. Databricks 문서의 구성 요소 목록을 이 네 요소에 대응시켰습니다.

    구성 요소 하는 일 문서상 대응 요소 이 장의 페이지
    모델 다음 행동을 추론하고 답을 생성 Unity Gateway(모델 접근), Foundation Model APIs 배포와 인증
    도구 실제 작업 실행 (조회, 계산, 외부 호출) UC 함수, MCP 서버(관리형·외부·커스텀), AI Functions 도구: UC 함수와 MCP 서버
    메모리와 상태 한 대화의 진행 상황(세션)과 여러 대화에 걸친 사실(메모리)을 보관 에이전트 세션, 에이전트 메모리 (Lakebase 기반) Agent Bricks CLI로 에이전트 개발하기
    오케스트레이션 추론과 도구 호출의 반복 순서를 관리하고, 실행 중 상태를 잃지 않게 함 에이전트 코드(LangGraph, OpenAI Agents SDK 템플릿), DurableAgentServer Agent Bricks CLI로 에이전트 개발하기

    오케스트레이션은 Databricks가 자동으로 정하지 않습니다. 개발자가 에이전트 코드에서 루프의 순서와 종료 조건을 정합니다. 문서는 프레임워크 템플릿으로 LangGraph와 OpenAI Agents SDK를 제공합니다. 템플릿 안에서 실행 상태를 지키는 역할은 DurableAgentServer가 맡는다고 문서가 설명합니다. 이 서버는 실행 상태를 Runtime Store에 보존하도록 구성됩니다.

    헷갈리기 쉬운 용어¶

    에이전트 문서에는 비슷해 보이는 용어가 많습니다. 아래 구분은 공식 문서의 설명을 따릅니다.

    용어 무엇을 담는가 수명 어디서 다루는가
    세션 (agent session) 한 번의 상호작용 상태. 주로 대화 기록(메시지, 도구 호출과 결과) 한 상호작용 또는 한 대화 Agent Bricks CLI
    메모리 (agent memory) 여러 대화에 걸쳐 회상할 사실, 선호, 결정. 의미 검색으로 꺼냄 여러 대화에 걸침 Agent Bricks CLI
    트레이스 (MLflow trace) 에이전트 한 번의 실행을 단계별로 기록한 것 실험에 기록 트레이싱·평가·피드백
    추론 테이블 (inference table) 요청과 응답의 전체 페이로드 저장소 보존 정책에 따름 가드레일·거버넌스·모니터링

    세션과 메모리는 독립된 저장소입니다. 문서는 세션을 지워도 메모리는 남는다고 설명합니다. 두 저장소는 Lakebase 위에 있다고 문서가 명시합니다.

    기본 루프¶

    에이전트 루프는 보통 다음 순서로 반복됩니다.

    단계 하는 일 구성 요소
    추론 사용자 요청과 대화 이력을 보고 다음 행동을 정함 모델
    컨텍스트 조회 필요한 문서나 과거 대화를 찾아 프롬프트에 넣음 AI Search, 메모리·세션
    도구 호출 선택한 도구를 인자와 함께 호출 도구
    관찰과 판단 도구 결과를 보고 종료할지, 다시 호출할지 정함 모델, 오케스트레이션
    응답 결과를 종합해 답하고 실행 기록을 남김 오케스트레이션, 트레이싱

    문서의 Python 예시는 도구 호출 루프를 10회로 제한합니다. OpenAI 클라이언트 방식의 MCP 예시에서 "capped at 10 iterations"라고 적혀 있습니다. 무한 반복을 막는 상한은 개발자가 직접 둬야 합니다.

    언제 쓰는가¶

    모든 문제에 에이전트가 필요하지는 않습니다. 기준은 다음 단계가 실행 중에 결정되는지 입니다. 단계 순서가 미리 정해져 있으면 파이프라인이 더 단순하고 예측하기 쉽습니다.

    방식 적합한 경우 예 피할 이유
    단일 모델 호출 입력 하나를 변환하거나 요약하면 끝나는 작업 문장 분류, 요약, 번역 도구 호출이나 상태가 필요 없음
    AI 함수로 행 단위 처리 테이블의 각 행에 같은 프롬프트를 적용 ai_query로 행마다 분류 (05장 AI Functions) 행마다 다음 행동을 고를 필요가 없음
    결정적 파이프라인 단계 순서와 데이터 흐름이 고정 스케줄된 노트북이나 작업 흐름 입력에 따라 경로가 달라지면 고정 순서가 깨짐
    RAG (고정 검색) 질문마다 검색 한 번 후 답하는 구조가 고정 사내 문서 Q&A, 검색 후 답변 검색을 다시 할지, 어떤 인덱스를 고를지 판단해야 함
    에이전트 (코드) 다음 행동을 실행 중에 정해야 하고 여러 도구를 조합 여러 데이터 소스를 조회해 원인을 분석 단순한 작업에는 지연 시간과 비용이 과함
    에이전트 (저코드, Genie Agents) 테이블과 문서에 대한 자연어 질문 데이터 분석가가 설정한 도메인 질의 에이전트 로직을 직접 제어해야 할 때

    RAG와 에이전트의 차이는 검색 단계가 고정되어 있는지 입니다. 고정 RAG는 검색 후 생성의 순서가 정해져 있습니다. 에이전트는 검색을 할지, 어떤 인덱스를 고를지, 결과가 부족하면 다시 찾을지를 모델이 정합니다. 두 방식을 섞을 수도 있습니다. 예를 들어 에이전트가 AI Search 인덱스를 도구 하나로 쓰는 구성입니다.

    Genie Agents는 문서가 "테이블과 문서에 대한 질문에 답하는 저코드 방식"이라고 정의합니다. 이 장에서는 에이전트 분류에 넣지만, 개발자가 루프를 짜지 않고 데이터 분석가가 설정으로 만든다는 점이 다릅니다. 자세한 비교는 Databricks 에이전트 제품 지도에서 다룹니다.

    참고 에이전트는 호출마다 모델을 여러 번 부르므로 같은 질문도 단일 호출보다 토큰 비용과 지연 시간이 큽니다. 작업이 한두 단계로 끝나면 에이전트를 쓰지 않는 편이 낫습니다.

    흔한 실패 유형과 대응¶

    에이전트가 실패하는 방식은 대개 몇 가지로 나뉩니다. 각 실패의 원인을 찾으려면 실행 경로를 기록하고 품질을 점수로 봐야 합니다. 이 장에서는 기록과 평가를 트레이싱·평가·피드백 페이지에서 다룹니다.

    실패 유형 증상 원인 후보 대응
    도구 선택 오류 필요 없는 도구를 호출하거나 맞는 도구를 놓침 도구 설명이 모호하거나 도구가 너무 많음 도구 설명 정리, 도구 수 줄이기, 평가 질문으로 회귀 확인 (트레이싱·평가·피드백)
    인자 오류 도구는 호출되지만 잘못된 값으로 실패 스키마와 프롬프트의 불일치 도구 입력 스키마를 명확히 하고, 실패 트레이스를 기준으로 테스트 추가
    근거 부족 검색 결과가 질문과 무관하거나 비어 있음 청크 설계, 인덱스 유형 선택, 검색 모드 검색 모드(hybrid) 검토, 인덱스 소스 점검 (AI Search와 검색 기반 에이전트)
    권한 실패 "권한 없음" 또는 빈 결과 호출 주체가 앱 서비스 프린시펄인지 사용자인지 혼동 도구의 auth 값과 권한 부여 대상을 먼저 확인 (배포와 인증)
    품질 저하 같은 질문에 응답 품질이 떨어짐 모델·프롬프트·데이터 변경 골든 데이터셋 평가, 프로덕션 모니터링 (트레이싱·평가·피드백)
    비용과 용량 문제 특정 사용자나 작업이 예산을 초과 루프 반복 횟수, 과도한 호출 속도 제한과 사용량 추적 (가드레일·거버넌스·모니터링)
    무한 반복 도구 호출이 끝나지 않음 종료 조건 부재 반복 상한을 코드에 두기 (위 예시처럼 10회 상한)
    안전 문제 민감 정보 노출, 프롬프트 인젝션 입력·출력 검사 부재 서비스 정책(Beta) 검토 (가드레일·거버넌스·모니터링)

    참고 위 표의 대응 중 "반복 상한", "도구 설명 정리" 같은 항목은 일반적인 설계 원칙입니다. 문서가 권장 값을 명시한 항목은 Python 예시의 10회 상한 하나뿐입니다.

    트레이드오프¶

    • 유연성 대 예측 가능성: 에이전트는 실행 경로가 매번 다를 수 있습니다. 같은 입력에도 다른 도구 순서가 나올 수 있으므로 평가와 트레이싱이 필수입니다.
    • 권한 범위: 에이전트가 도구로 접근하는 데이터를 누구의 권한으로 읽는지가 핵심입니다. 앱 서비스 프린시펄로 실행할지, 호출한 사용자 권한으로 실행할지에 따라 결과가 달라집니다.
    • 구현 방식: 코드 방식(Agent Bricks CLI)은 제어가 세밀하지만 개발 역량이 필요합니다. 저코드 방식(Genie Agents)은 설정으로 끝나지만 에이전트 로직을 직접 제어할 수 없습니다.
    • 운영 부담: 배포 후에는 품질 모니터링, 사용량, 정책 검토가 계속 필요합니다. 한 번 만들고 끝나는 구조가 아닙니다.

    어떻게 쓰는가¶

    Databricks에서 에이전트를 시작하는 가장 짧은 경로는 Agent Bricks CLI로 프로젝트를 만드는 것입니다. 명령과 구조는 Agent Bricks CLI로 에이전트 개발하기에서 설명합니다. 이 페이지는 설계 단계에서 쓰는 체크리스트입니다.

    1. 에이전트가 해결할 작업을 한 문장으로 적습니다. 단일 호출, 결정적 파이프라인, RAG로 충분한지 먼저 확인합니다. 충분하다면 그 방식을 씁니다.
    2. 필요한 데이터 소스와 도구를 나열합니다. 각 도구의 호출 주체(앱 서비스 프린시펄 또는 호출 사용자)를 함께 적습니다.
    3. 대화 상태가 한 번의 상호작용 안에서만 필요한지, 여러 대화에 걸쳐 필요한지 구분합니다. 전자는 세션, 후자는 메모리입니다.
    4. 평가 질문 세트(골든 데이터셋)를 먼저 만듭니다. 구현 후 개선 여부를 판단하는 기준이 됩니다.
    5. 배포 후 감시할 지표(품질 점수, 도구 오류율, 사용량)를 정합니다.

    주의사항¶

    주의 일부 에이전트 제품은 Legacy로 표시되어 있습니다. Knowledge Assistant와 Supervisor Agent가 해당합니다. 새 에이전트는 공식 문서가 안내하는 현재 제품으로 만드십시오. 자세한 대체 경로는 Databricks 에이전트 제품 지도에 있습니다.

    참고 Databricks 문서의 에이전트 페이지는 제품 명칭과 경로가 자주 바뀝니다. 학습 자료의 제품명은 공식 문서 표기를 따르고, 구 명칭은 처음 한 번만 괄호로 병기합니다.

    • 쓰기 권한을 가진 도구는 승인 절차 없이 연결하지 않습니다. 서비스 정책(Beta)은 가드레일·거버넌스·모니터링에서 다룹니다.
    • 도구 호출 로그와 트레이스를 처음부터 남기십시오. 사후에 원인을 추적하기가 매우 어렵습니다.
    • 반복 상한과 타임아웃을 코드에 명시하십시오. 종료 조건이 없는 루프는 비용을 계속 늘립니다.
